# Repository instructions

## Authority

Follow the canonical specification `docs/canonical/specification.json` (schema `docs/canonical/specification.schema.json`; layer definitions `docs/canonical/LAYERING.md`) for product behavior. Within it, authority descends by layer: `root` (Owner rulings) → `request` → `require` → `spec` → `detailed_spec` → `basic_design` → `design`. Add a norm to a lower layer only when the layers above it contain that norm, because a norm without an upstream has no derivation to check. When a lower layer needs a norm the upper layers lack, feed the gap upstream; when layers conflict, resolve in favour of the higher layer and feed the conflict upstream.

Read `docs/canonical/export/*.md` as generated readings of the same data, and take the JSON as the authority, because the exports may lag it. The markdown documents under `docs/archive/` are the retired pre-conversion sources; cite the canonical JSON for norms, and when a claim appears only in `docs/archive/`, look for it in the JSON or report it as unresolved.

Use an implementation schedule as process material only when planning requires it, and take the documents above as the authority, because a schedule is not a normative product source and an override by it makes the product contract drift. If active normative documents disagree or leave a required decision open, cite the exact sections and report the unresolved contract. The decision comes from the canonical documents or, when they are silent, from upstream: report the gap, because historical files, tests, implementation behavior, and Git history show what was done and not what was decided.

Follow `DEVELOPMENT.md` for Git flow, branch naming, tags, and shared-history policy. It is the separate, sole repository authority for them and is not a product-behavior authority. Read it when a Git-flow question arises, because a restatement of its rules here would diverge from it.

## Product invariants

- Verification has exactly four checks: `chain_integrity`, `orphan_detection`, `target_binding`, and `oracle_presence`. Keep these four checks as the only checks when adding document layers, evidence sources, diagnostics, judgments, or approval rules, because each is another instance of the same trace and not a new check.
- Verification has exactly five states: `PASS`, `FAIL`, `MISMATCH`, `NO_EVIDENCE`, and `UNKNOWN`.
- Treat `MISSING`, `NOT_EXECUTED`, `NOT_CHECKED`, and `STALE` as diagnostic labels attached to a state, because a state exists only when it changes what the receiver does. Keep state, diagnostic label, diagnostic severity, operation error, aggregate OK/NG, and gate satisfaction as distinct fields and concepts.
- Keep work outside the requested scope from counting as `PASS`, because out-of-scope work has no evidence and `PASS` would claim it. Omitted checks represented in the aggregation tree remain `NO_EVIDENCE` with `NOT_CHECKED`. Entity scope outside the request remains explicitly unverified through the canonical scope representation, outside the aggregate. When you report a limited result, say that it is a limited result and not complete verification.
- Express every upstream normative artifact, including a new document type, with the generic `document` model connected by `derives_from`, because document-type-specific canonical entities and schemas multiply checks.
- Treat Judgment and Approval as independent domains that may be independent entities. Recording or accepting either leaves the verification state as it was, because neither is evidence and a record that moves a state would change the verdict. Treat Judgment completion as separate from Approval.
- Use `vtest approval create`, `vtest approval withdraw`, and `vtest approval show` as the canonical Approval CLI. Treat `vtest vo approve` as an alias of Approval creation with identical semantics, because two semantics for one operation would let the same command mean different approvals.
- Evaluate verification state and gate satisfaction as separate axes. With `--gate`, exit code `0` and top-level `ok: true` may mean that the named gate is satisfied; read the actual aggregate verification state separately and always expose it, because a satisfied gate can coexist with a state other than `PASS`.
- Return a non-`PASS` state for missing, stale, ambiguous, incomplete, unsupported, or unanalyzable inputs, because a fallback to `PASS` hides what is unproven. Use `UNKNOWN` as a deterministic limit, because it sends the receiver to someone who can judge meaning while an internal error needs a fix and mixing them hides defects. Report operation rejection and internal failure outside the five-state model.
- Emit `PASS` or `FAIL` from static or other deterministic analysis only when the applicable canonical rule establishes that result, because inability to prove the opposite is not proof.
- Let compatibility readers and wire adapters affect a result only after their data is normalized into the current canonical model and passes every current invariant, because legacy data can carry weaker rules. Reconstructing canonical truth, selecting an ambiguous candidate, weakening scope, or bypassing freshness and aggregation each defeat that normalization.
- Keep canonical and derived data separate: regenerate derivable graphs, indexes, static-analysis results, bundles, and reports from canonical records, because a derived artifact that becomes a source of truth can disagree with the canon silently. When a derived artifact looks wrong, find the cause first: regenerate it when it is stale, fix the generator when the generator is defective, and change the canonical record only after the canonical error is confirmed, through the specification-change procedure in `DEVELOPMENT.md`.
- Bind Evidence, Judgment, and Approval validity to the complete current subject and dependency closure required by the canonical design. Keep historical records readable as history; they become effective current evidence only when bound to the current closure.
- Put language-specific discovery, analysis, editing, execution, and coverage behind adapter capabilities, and supply no language-specific default in core domain or wire behavior when an adapter or capability is absent, because an invented default would hide the gap. When an explicit operation lacks a required capability, reject it as an operation error (`E-ADAPTER-004`) without changing anything or creating a Judgment or Evidence record; when verification lacks a capability, report the corresponding state and diagnostic (`NO_EVIDENCE` with `NOT_CHECKED` or `NOT_EXECUTED`).
- Map each assertion of acceptance evidence explicitly to the current canonical clauses and observables before calling it current canonical conformance. Use historical or superseded acceptance evidence as regression evidence only; when conformance is needed, produce new evidence mapped to the current clauses.
- Describe behavior as implemented, verified, accepted, or release-ready only when current implementation evidence demonstrates the applicable canonical contract, because an unevidenced claim is the false `PASS` this tool exists to stop. When evidence is missing, state what is not demonstrated.

## Agent operating rules

- Before changing behavior, read the applicable authority sections from requirements through acceptance criteria, and preserve upstream-to-downstream traceability. When the sections contradict, cite the clauses and feed the contradiction upstream, and choose a rule after upstream decides, because a silently chosen rule changes the contract without review.
- Before any review, state the review target, purpose, fixed decision axes, and exclusions. If no existing axis applies, define the appropriate axis before reviewing. Keep the axes as declared throughout the review, because a changed axis hides a failure behind a new standard. When an axis is deficient, report it separately and continue with the declared axes.
- Reject work for failures within the declared axes. Within an axis, report every material issue; the number of findings is not itself over-review. Concerns outside the axes belong to another review contract; when one is a material canonical or safety violation, follow the next rule.
- Report a material canonical or safety violation found outside the declared axes as an out-of-scope blocker, or re-scope explicitly, because silence or a ready decision would hide it. Return a decision other than ready while it is unresolved, and score it as an in-axis finding only after an explicit re-scope.
- Keep “changing the review axis” distinct from “finding a failure on the declared axis.”
- Judge a gate by whether the current phase can hand its responsibilities to the next phase correctly; flawlessness of the artifact is a different question. State the required handoff evidence and fail closed when it is absent, because a gate that demands perfection never passes and a gate without evidence passes everything.
- Separate direct observations from inferences. Give file/section or command evidence for findings, and label unresolved canonical questions instead of guessing, because a reader cannot check an inference presented as a fact.
- Inspect the current implementation and tests, and take the canonical documents as the authority over their behavior, because behavior records past decisions that may be wrong. When the worktree holds legitimate user changes outside your task, leave them in place.
- For verification and release decisions, use the project Skills in `.agents/skills/`. Recreate a removed helper script only when a new deterministic procedure is fully derivable from the current canonical contract and current implementation, and validate any helper you add, because an unvalidated helper becomes an unreviewed source of results.
- Run checks in proportion to the changed surface. The repository development gate is defined in `DEVELOPMENT.md` and `TESTING.md`; collect canonical conformance evidence separately, because the gate shows code quality and not conformance to the canonical contract.

## Writing rules for instructions and documents

- Write each rule in this order: the action to take; the reason; the situations that can arise and the action for each. In short: "Do X. Reason: Y. Because Z can happen, in case W do V." Keep this order in every language.
- Express a prohibition as the action that serves the same end, with its reason and the case-specific action. For example, replace "Do not cite archived documents as norms" with "Cite the canonical JSON for norms, because the archive is retired; when a claim appears only in the archive, look for it in the JSON or report it as unresolved."
- Check a rewritten rule by asking what the reader does in the situation the old prohibition guarded; when that is unclear, rewrite it again. A rule passes when the reader knows the action, not when the negation is gone.
- Remove a sentence that carries no action, reason, or condition (for example "The specification is not a premise."), because every token of an instruction file is read in every session.
- Apply these rules to instructions. A statement of fact about the product (a feature description, a changelog entry, a canonical clause) stays a statement of fact.
