## 0. 枠

### 0.1 対象・目的・軸・除外（調査中に変更しない）

- **対象**: `DES-572`「節ノードは子ノードの subject hash を束縛する」が、子をどの順で encode するかを定めていない穴。
  実装 PR #20 はここで止まっている（実装で選ばず `Vec` のまま停止）。
- **目的**: 正本の側で順序を確定するか、確定できないなら争点を Owner へ出す。
- **軸 A（層の権威）**: その規範は、どの層に明文があるか。上位に明文があれば下位は具体化として正当、
  上位に無ければ下位の発明を疑う。層順は `root` → `request` → `require` → `spec` → `detailed_spec` → `basic_design` → `design`。
- **軸 B（目的からの演繹）**: 明文が無いとき、Issue #11 F1（`ROOT-*`）と上流ノードから演繹できるか。
- **軸 C（嘘テスト）**: その規則があると、偽のリンク・偽の PASS が通るか、鎖の切れ目が隠れるか。
- **除外**: 実装コード。実装の現状を根拠に正本を解釈しない。実装コストを理由に規範を選ばない。
  節ノードが自身の `id` / `title` を束縛するかは別の問い（§6 に所見として出すだけで、本書では変更しない）。
- **表記**: **明文** = 正本ノードの逐語。**導出** = 演繹。**実測** = 本日 `specification.json` を走査した数値。

### 0.2 場面（何が壊れると困るのか）

節ノードの subject hash は、承認・判断記録の失効判定に入る。

- **DES-576**（明文）: 承認レコード a が有効であるには `a.subject_hash` が現在の内容ハッシュと一致し、
  `a.dependencies` の各 document ノードについて記録された束縛ハッシュが現在の subject hash と一致しなければならない。
- **DES-578**（明文）: `approved` から `draft` への遷移は、上流依存 closure のいずれかの hash が変化することで起きる。
- **DS-1613 / DS-1615**（明文）: 束縛ハッシュと現在の subject hash が不一致なら `chain_integrity = MISMATCH`（診断 `STALE`）。

したがって「規範が変わったのに節の hash が変わらない」は、**承認が生き残る＝偽の PASS が通る**経路である。
これは F1（`ROOT-*`、AI の完了宣言の受領時に嘘の PASS を止める）が守ろうとしている当の瞬間にあたる。

| 候補 | 規則 | 並べ替えで節の hash が変わるか |
|---|---|---|
| (a) 宣言順 | 子の subject hash を文書ファイルの配列順で encode（`DES-075` の類推） | **変わる** |

## 3. 嘘テスト

`.verify/doc/` に正本を登録し、節 `BD-S038`（`2.1 .verify/ レイアウト`、19 文）を上流依存 closure に含む承認が 1 件 `approved` である状態を初期状態とする。

### 3.1 節内で子を並べ替える

実在の例を使う。`BD-S038` の配列順は次のとおり（実測）。

```
BD-136, BD-137, BD-323, BD-139 … BD-148, BD-149, BD-150, BD-151, BD-152,
BD-153「vtest init は上記ディレクトリ、config.yaml の雛形、… を生成する。」,
BD-330
```

`BD-153` の「上記ディレクトリ」は、その前に並ぶ `BD-137`〜`BD-148` の列挙を指している。
`BD-153` を節の先頭（`BD-136` の前）へ動かすと、**`vtest init` が何を生成する義務なのかが変わる**（指示対象が消える）。
このとき各文ノードの `id` と `statement` は 1 文字も変わらないため、`DES-572` の文ノード規則では捕捉できない。

| 候補 | 節 hash | 承認 | 判定 |
|---|---|---|---|
| (a) | 変化する | 失効し、Owner が再裁定する | 正しい |
| (b)(c)(d) | **変化しない** | **`approved` のまま生存** | **偽の PASS が通る** |

同型の文は正本に 9 件実在する（実測）。

`BD-153`「上記ディレクトリ」 / `DS-951`「上記例の固定順」 / `DS-1318`「上記の各入力」 / `BD-231`「上記のいずれか」 /
`DS-1215`「同上の入力」 / `DS-1166`「上記解決規則」 / `DS-1518`「上記の出力」 / `BD-014`「上記から」 / `SPEC-425`「上記の各値」

**この 1 件で (b)(c)(d) は落ちる。**

### 3.2 子を別の節へ移す

`BD-153` を `BD-S038` から別の節へ移す。移動元・移動先の双方で子の集合が変わるため、
節 hash は **(a)(b)(c)(d) のいずれでも変化する**。判別しない。

なお移動は `LAYERING.md` §1.1「文の実効的な上流 = 自分の辺 ∪ 先祖（節・文書）の辺」により
当該文の実効的上流も変えるが、その変化は移動先・移動元の節 hash で既に捕捉される。

### 3.3 子を追加・削除する

子の集合が変わるため **(a)(b)(c)(d) のいずれでも変化する**。判別しない。

### 3.4 子の `statement` を変える

子の subject hash が変わり、親へ伝播する。**いずれでも変化する**。判別しない。
`DS-1610`（明文）と一致する。

### 3.5 子の `description` だけを変える（逆方向テスト）

`DES-572` により `description` は束縛されない。子の hash は変わらず、親も変わらない。
**いずれでも変化しない。** `DS-1599`・`DS-1609`（明文）と一致する。(a) を採っても崩れない。

### 3.6 (a) の逆方向テスト — 意味の無い変更で hash が変わるか

意味を変えない純粋な編集上の並べ替え（`上記` 等の照応を含まない節での入れ替え）では、
(a) は節 hash を変え、当該節を closure に含む承認を失効させる。これは過剰失効である。

ただしこれは**閉じる方向の誤り**であり、`ROOT-031`「fail-closed の『証拠なし ≠ PASS』が全ケースを拾う」
および `AGENTS.md`「Missing, stale, ambiguous, incomplete … never become `PASS` by fallback」の許す側に落ちる。
過剰失効は Owner の再裁定を求めるだけで、嘘を通さない。

「照応を含む並べ替えだけを束縛する」案は成立しない。ある並べ替えが意味を変えたかの判定は
自然言語の意味判定であり、`ROOT-030`「発見する知能は載せない。発見者は外部」に正面から反する。
**判定できない以上、一律に束縛する以外に選べない。**

### 3.7 (c) の追加的な欠陥 — `id` 順は文書の並びではない

`id` 番号順と配列順が一致しない節は、2 件以上の文を持つ 365 節のうち **45 節**（実測）。
`id` は変換と退役の履歴で付き、文書上の位置を表さない（`DS-1635` が `DS-969` と `DS-971` の間に入る等）。
(c) は仮に順序を束縛できたとしても、束縛する順序が文書の並びと別物になる。

## 4. 判定

**導出で決まる。Owner 裁定は不要。** 論法は 3 段。

1. `ROOT-031`・`REQ-115`・`REQ-241`・`REQ-335`（明文）: 承認・判断は対象の**規範内容**から計算した subject hash に束縛され、規範内容が変われば失効しなければならない。
2. 実測（事実）: 兄弟の並びは、正本の 9 件の文で規範内容の一部になっている。並べ替えは文ノードの `id`・`statement` を変えないため、節ノードの subject hash が唯一の捕捉地点である。
3. `ROOT-030`（明文）: 並べ替えが意味を変えたかを vtest は判定しない。したがって一律に束縛する。

⇒ **(a) 宣言順**。

論法が全候補を落としていないことを確認した: §3.5 と §3.6 で (a) 自身に逆方向テストを当て、
`description` 変更の非伝播（`DS-1599` と一致）と、過剰失効が fail-closed 側であることを示した。
(b)(c)(d) を落としたのは論法ではなく §3.1 の実在ノードである。

## 5. 適用

`design` 層 `DES-S031`（`1.3 内容ハッシュの定義`）の `DES-572` の直後に 1 件追加した。
`DES-572` の `statement` は変えていないため id は維持、退役台帳への記載は不要。

**新規 `DES-587`**

> 節ノードの subject hash は、子を `items`（文ノードの列）と `sections`（下位節ノードの列）の 2 つの名前付き順序列として束縛し、各列を当該配列の宣言順で encode する。空の列も空 list として明示し、省略しない。

`derives_from`: `ROOT-030`, `REQ-115`, `REQ-241`, `REQ-335`（すべて上位層。同層への辺なし）
`description`: 導出であることの明示、上流探索の結果、却下した候補と根拠、`source.lines` を順序の権威にしない理由、§6 の開示。

補って確定させた 2 点（実装が再び止まらないため）:

- **`items` と `sections` を混ぜない。** 2 つの名前付き field として別々に束縛する。
  `DES-071`（field は `field-name`・UTF-8 byte length・byte 列の順に encode）に従えば列ごとに field 名が付き、
  両者の混合順を新たに定義する必要がない。両方を非空で持つ節は **24 節**実在する（実測）。
- **順序の権威は文書ファイルの配列であって `source.lines` ではない。**
  `source` は移行期間限定 field（`specification.schema.json` の逐語）であり subject hash に束縛されない。
  実測でも 365 節中 2 節（`BD-S038`・`DES-S036`）で配列順と `source.lines` 順が不一致で、
  これは後から挿入したノード（`BD-330`・`DES-585`・`DES-586`）が
  元の見出し行を指しているために起きている。配列順は 365 節中 **363 節**で `source.lines` 順と一致する。

## 6. 開示（本書では直さない所見）

いずれも本変更の範囲外であり、`DES-587` と矛盾しない。上流へ差し戻す対象として記録する。

### 6.1 `detailed_spec` に節ノードの不変条件が無い（穴）

`DS-1601` / `DS-1610` / `DS-1612` は「規範内容（`id` と `statement`）」と書いている。
括弧を網羅的な定義と読むと、`detailed_spec` だけを読んだ実装者は
「節ノードの子の並べ替えは規範内容の変更に当たらない」と結論する。

3 件はいずれも**文ノードについての十分条件**であって節ノードに触れていないため `DES-587` と矛盾しないが、
「節の子の並べ替えは規範内容の変更である」という不変条件は、不変条件が置かれるべき `detailed_spec` 層に無い。
`LAYERING.md` §2 の代表例が「『〜に束縛される』型の不変条件は詳細仕様」と定めているため、
この WHAT は `detailed_spec` に 1 文必要である。**提案**（決定ではない）:

> 節ノードの子の並び順は当該節の規範内容に含まれ、子の集合を変えない並べ替えでも当該節の subject hash が変化して、当該ノードを上流依存 closure に含む判断記録・承認は失効する。

### 6.2 節ノードの hash が自身の `id` と `title` を束縛しない（所見）

`DES-572` は節ノードについて子の subject hash だけを束縛する。したがって節の `title` の変更
（例: `1.3 内容ハッシュの定義` → `1.3 ハッシュ規則`）は節 hash を変えない。

これは現時点で嘘の経路ではない。`DES-576` が `a.subject == X`（承認の対象指定が対象と一致すること）を
別途要求しているため、子集合が同じ 2 節の hash が衝突しても承認が別の節へ移ることはない。
`title` が規範を運ぶか（`description` と同じ非束縛でよいか）は本書の対象外の問いとして残す。

### 6.3 `DES-572` 自身の `derives_from` が空（所見）

`DES-572` の `derives_from` は空で、実効的上流は親節 `DES-S031` の辺から来ている。
`root` 外で実効的上流が空のノード 270 件には数えられないが、
文の粒度では上流が `SPEC-S002` 等の節 15 件に薄く広がっている状態である。本書では触っていない。
