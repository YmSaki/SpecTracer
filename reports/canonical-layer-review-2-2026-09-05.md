## 4. 判定で適用した線引き（観測の再現用）

第1回 §4 の 5 本をそのまま当てた。すなわち、メタ記述は NONE／不変条件は詳細仕様／外部入力・外部出力の形式は詳細仕様で内部の型と保持状態は詳細設計／実現手段を名指しした文は設計／由来文書（`source.doc`）は根拠にしない。今回の標本で新たに必要になった線引きは次の 4 本で、所見であって推奨ではない。

- **集合の外延か、恒真の性質か。** 「提供する検査・機能・編集手段の集合に X が含まれない」型の否定文は 基本仕様「提供する機能」（範囲画定）。「ある概念が常に／決して〜である」型の恒真文は 詳細仕様「仕様上の不変条件」。前者に当たるのが `DS-154` / `DS-174` / `DS-254` / `DS-334`、後者に当たるのが `DS-014`（検証状態は検証結果のみを表す）/ `DS-194` / `DS-734` である。
- **検査の有無か、検査の対象範囲か。** 検査そのものを設けるか否かは 基本仕様「提供する機能」。既にある検査が何を対象に取るかは 詳細仕様「すべての入力条件」。`DS-114`（対象は文書層のみ）と `DS-314`（参照位置の意味的妥当性は検査対象としない）は後者として OK とした。
- **結論が外部観測可能な状態か、内部データの保持か。** `ManagedTestLink` のような core 内部型を名指す文でも、結論が検証状態（`chain_integrity` の成立など）なら 詳細仕様「受入条件・検証可能な期待結果」、結論が entity の保持・除去なら 詳細設計「事後条件」。`DS-1274` は前者として OK、`DS-554` は後者として MOVE とした。
- **状態集合への所属は基本仕様、状態遷移の条件は詳細仕様。** `SPEC-374`（`NO_EVIDENCE` は状態であって診断ラベルではない）は状態集合の画定として 基本仕様「外部から観測可能な状態変化」で OK、`SPEC-314`（変更そのものが `UNKNOWN` を生成するのではない）は生成条件の否定として詳細仕様へ MOVE とした。

- **用語定義は、その語が外部インターフェースに現れる概念を画定するなら基本仕様。** `SPEC-014`（VO とは独立に検証可能な仕様上の命題である）は、利用者が宣言する VO の意味を画定するものとして 基本仕様「外部から与えられる入力」で OK とした。参照文書の一覧に「用語定義」という項目は無いため、語が指す対象が入力・出力・状態のどれに当たるかで置く。

判定が割れた境界事例を 3 件、記録として残す。

- `DS-374`（document レコードの `derives_from` は 0 件も許容し、0 件は根候補を意味する）は 詳細仕様「入力値の範囲・形式・制約」として OK とした。第1回が field の**構成**（`SPEC-267`）を design へ送ったのに対し、これは利用者が書けるレコードの field の**許容件数**であり、構成ではないという理由による。
- `DES-434`（`impl-consistency` 型の判断バンドルに document subject 完全集合と source 全文を加える）は 詳細設計「構成要素ごとの責務」として OK とした。バンドルは外部エージェントへ渡る成果物だが、第1回がレコードの内容（`SPEC-267`・`DES-054`）を design 側に置いているため、読み取り可能な成果物の内容構成は design で一貫させた。
- `DES-034`（Target Reference は adapter ID と opaque locator の組、または SRC ID 参照である）は 詳細設計「入出力データの構造」として OK とした。利用者が annotation で宣言する形でもあるため 詳細仕様「入力値の範囲・形式・制約」に当たりうるが、第1回が `DES-207`（path の書式）を移したのは文字列の**書式**であり、これは型の variant 構成であるという理由で design に残した。

`LAYERING.md` L48–L55 の PM 仮置きのうち「`E-SCAN-016` は外から見える体系 → basic_design」は今回の標本では採らなかった。診断コード表の行（`DS-894` / `DS-914`）は 詳細仕様「エラーの外部的意味」により特定的に当たり、`LAYERING.md` §2 の一覧項目優先の規則が仮置きに優先するため OK とした。
