### 3.1 F — 導出表の P-00N / NFR-00N / OOS-00N が解決できていなかった（適用済み）

要求→要件 導出表の上流欄・下流欄は `P-001`、`NFR-003`、`OOS-001` のようなコードで

していたが、CONVERSION.md §2.1 の列挙分割がコードを文頭から文末の括弧内へ移したため、
どの文にも当たらず行が丸ごと落ちていた。辺の新設ではなく解決漏れの復旧である。

- **P-00N（下流側のみ）**: 導出表の前書き「節は表示上のグループであり、導出の単位は
  規範文である」に従い、当該 P-00N 見出し配下の require 規範文へ配る。上流側は
  LAYERING.md §1.1「表を文単位に展開しない」に従い `P-00N` ノード1つのままとした。
  上流側にも配れば 23 ノードが 36 辺を追加で得るが（実測）、これは失敗した解決の修復では
  なく成功した解決の拡張なので**適用していない**（→ 問い3）。
- **NFR-00N / OOS-00N（両側）**: 要件定義 §24・§25（コードの定義箇所）の中で当該コード
  を含む規範文へ解決する。§26.4 が `OOS-004` を参照するだけの文（REQ-306）は定義では

### 3.2 B — 上流は表に明記されているが、上位層に対応ノードが無い（144 件、報告のみ）

**この 144 件が残存孤児の 59%** であり、単一の原因を持つ。

トレーサビリティ表は「この節は上流**文書**のどの節を実現するか」を記録する。一方 2026-09-05
の再仕分け（LAYERING.md §2）は、文を**文書**ではなく**層**へ割り当て直した。その結果、
詳細設計 md の文の多くが `spec` 層へ上がった一方、それらが表で名指ししている上流
（基本仕様 §N、本冊 §N）の文も `spec` 層以下に置かれた。辺は層をまたぐ上向き参照だけ
なので（LAYERING.md §1.1、`finalize_derived_from` の規則3）、行は存在するのに辺が
1本も立たない。

由来文書 × 層の内訳（B と D の 148 件）:

| 層 | 由来 md | 件数 |
|---|---|---|
| spec | 詳細設計 本冊 | 60 |
| spec | 詳細設計 別紙A | 39 |
| spec | 詳細設計 別紙C | 31 |
| require | 要求・要件定義 | 14 |
| detailed_spec | 詳細設計 本冊 | 4 |

上流の解決先がどこに落ちたかで3つに分かれる。

- **B1 同一層のみ（16 件）** — 表の行が同一層内の詳細化を記録している。例: 要求→要件
  導出表 L685「上流: §10.1 / 下流: §10.4 VO:Test = N:M」。§10.1 も §10.4 も require 層
  なので辺にならない。該当: REQ-170〜173、REQ-206〜208、REQ-283、REQ-290、REQ-297、
  REQ-298、REQ-S033、REQ-S038、REQ-S055、SPEC-350、SPEC-S100。
- **B2 上流が下位層のみ（2 件）** — SPEC-336、SPEC-S097。文が自分の上流より上の層に
  置かれている、層の反転。
- **B3 同一層と下位層の混在（126 件）** — 大半がこれ。全 id は付録 A に挙げる。

**この 144 件はすべて、表のグラフを1段たどる推移閉包で解消する**（実測。1 hop で 144、
2 hop 以上を要するものは 0）。たとえば
SPEC-S071 の行は「上流: 基本仕様 §3.2」で、基本仕様 §3.2 の spec ノードはさらに

行を持たないため、**推移閉包では解消しない**（B の 144 件と違う点）。

## 5. Owner への問い

### 問い1 — 表のグラフを推移的にたどってよいか（144 件、残存孤児の 59%）

トレーサビリティ表 A→B と B→C の2行があるとき、A→C の辺を機械適用してよいか。

- **具体例**: SPEC-S071（詳細設計 §3.1 document レコードスキーマ、spec 層）の行は
  「上流: 基本仕様 §3.2」。基本仕様 §3.2 の spec ノードは「上流: 要件定義 §3.2」を持つ。
  合成すれば SPEC-S071 ← 要件 §3.2。どちらの表も直接には述べていない。
- **帰結（はい）**: 144 件すべてが孤児でなくなり、残存孤児は 99 件になる。ただし
  「`derives_from` は導出の証明ではなく参照であり、文書に書いてある引用先をそのまま繋ぐ」
  （Owner 2026-09-05）の「そのまま」を超え、機械が文書の言っていない対応を作ることになる。
- **帰結（いいえ）**: 144 件は孤児のまま残る。原因は表の書き方ではなく、2026-09-05 の
  層の再仕分けが文書の上下関係と層の上下関係を食い違わせたことなので、正しい直し方は
  **上流のトレーサビリティ表を層に合わせて書き直すこと**になる。

### 問い2 — 規範でない文を正本に残すか

§4.2 の 4 件（章の範囲宣言・分冊構成・文書の位置付け）は製品の振る舞いを述べていない。
LAYERING.md §2 は「現在の層に置いたまま所見として一覧に出す」としか定めておらず、退役
（削除）の規則は無い。残すのであれば、これらは恒久的に孤児として E-SCAN-016 を出し続ける。
消すのであれば規約（CONVERSION.md か LAYERING.md）に「変換後に規範でないと判明した
ノードの退役」規則が要る。

同じ問いが、より大きな形で **§3.3 の 72 件**（直下に規範文を1つも持たない見出しノード。
孤児の器すべてでは 74 件。全 id は付録 A）
にかかる。DS-1647 の「ノード」は節ノードを含むと読めるが、規範を1つも載せていない見出しが
上流を持たないことは、規範の切れ目ではなく木の形の反映である。**器の節ノードを
`orphan_detection` の対象に含めるか**は、正本を直す話ではなく検査の意味の話なので、
仕様側（DS-1647 / DS-1649 / SPEC 側の対応節）の裁定として挙げる。

### 問い3 — 上流側の P-00N も規範文へ配るか（23 ノード / 36 辺）
