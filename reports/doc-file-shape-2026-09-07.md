### 1.2 `BD-105` の「ULID ファイル名」は文書ファイルに及ぶか → **及ばない（既決）**

依頼が最初に判定を求めた点。**根拠は 3 本あり、いずれも既存条文である。**

1. **同じ層が ULID の適用先を列挙している。** `BD-S008`「3.1 エンティティ種別」が種別ごとに値域を割り当てている:
   `BD-023` Relation = `REL-`（ULID）／`BD-024` 判断記録 = ULID／`BD-025` 承認記録 = ULID／`BD-026` Execution Evidence = ULID。
   **ノード（`BD-318`）と VO（`BD-020` = `VO-`）には ULID を割り当てていない。**
   レイアウト側も同じで、`BD-139` は `VO-<NAME>.yaml`、`BD-141` は `<kind>.yaml`（Form Schema）である。
   **したがって `BD-105` の「ULID ファイル名」は §24.2 の追記型レコード（`BD-062`〜`BD-065`）を指す要約であって、全レコードの規則ではない。**
2. **上位層が命名の主体を人へ置いている。** `SPEC-043`（spec、basic_design より上位）は「DOC / VO / TEST の ID は**利用者（人間または AI）が命名する**」。
   ULID は機械生成であり、これに反する。層の権威は spec > basic_design。
3. **同層の後続裁定が識別の担い手を決めている。** `BD-322` は上流文書について「ファイル名は当該文書を**識別するもの**」とし、
   VO についてだけ「ファイル名を **VO ID** とする」と**書き分けている。**

### 1.3 では何が文書を識別するか → **ファイル名そのもの（既決 + 導出）**

`BD-322` の書き分けが答えである。**VO には ID があり、ファイル名がそれと一致する。文書には ID が無く、ファイル名が識別そのものである。**

依頼が挙げた 2 つの嘘テストを当てる。

| 依頼の候補規則 | 判定 | 理由 |
|---|---|---|
| 「同じ文書識別子が 2 ファイルに現れたら拒否」 | **不要** | 識別子がファイル名そのものなら、同一ディレクトリに同名のファイルは 2 つ存在しえない。重複はファイルシステムが閉じる。**識別子 field を別に置いたときだけ必要になる規則であり、その field を置かないことで消える。** |
| 「vtest は文書ファイルを改名しない」 | **不要** | `DS-1637`（id を採番し直さない）の根拠は「再採番は全ノードの `derives_from` を書き換えることを要し、取り違えると偽のリンクが `chain_integrity` を通る」である。**文書ファイル名を参照する辺は 1 本も無い**（`DS-1594`: ノードの `derives_from` は上流**ノード id** の並び／`BD-165`: `derives_from` は上流ノードへの唯一のリンク種別）。改名しても解決先の変わる辺が無いため、`DS-1637` の根拠は移らない。**嘘テストが要求しない規則は足さない。** |

**したがって新設するのは「識別子 field を持たない」という否定側 1 件**（`DES-585`、導出）。
`BD-322` が肯定側を既に持っているため、肯定側は新設しない。

### 1.4 ファイル名の形は何で縛られるか → **HOW（上位は沈黙）**

`root` / `request` / `require` / `spec` に上流文書のファイル名を定める条文は無い（先行報告 §2.1 の語別探索で `ファイル名` 0 件、`ディレクトリ` は節 title のみ）。
`BD-322` も「当該文書を識別するもの」までしか言わない。

**嘘テストでは名前と ULID が判別しない。** 4 検査（`chain_integrity` / `orphan_detection` / `target_binding` / `oracle_presence`）はどれもファイル名を入力に取らず、
`derives_from` の解決はノード id だけで閉じている。ファイルが消えれば依存ノードの辺が解決できなくなり `E-SCAN-012` / `DS-388` で落ちる（fail-closed）。これは名前でも ULID でも同じ。

**したがって HOW である。依頼の指示に従い Owner の言葉に合わせる。**
`ROOT-048` の Owner 逐語は文書を**名前**（要求・要件・基本仕様・詳細仕様・基本設計・詳細設計）で数えている。→ `BD-330`。

**文字集合・接頭辞は定めない。** `DS-048`〜`DS-051`（人間可読、`[A-Z0-9-]`、種別ごとの固定接頭辞、`TEST-<領域>-<連番>`）は
「**DOC / VO / TEST の ID**」を対象とする条文であり、§1.3 の判定（文書は ID を持たない）の下では文書ファイル名に掛からない。
`DOC-` の値域は `BD-318`（H-1）で死んでおり（`BD-329` の description）、接頭辞を要求すると死んだ値域を復活させることになる。
**この読み（`SPEC-043` の「DOC の ID」を現行モデルのノード id として読む）は本書が新たに始めたものではなく、`DS-1637` が既に採っている。**

### 2.2 判定: **HOW（`SPEC-149` / `REQ-309` が明文で下位へ委譲している）**

`REQ-333` / `SPEC-462` / `BD-325` の「層ごとのトップレベル配列」は**保存形式ではなくモデルの記述**である。
これは本書の新しい読みではなく、先行報告 §2.3 が `BD-312`（→ `BD-325`）について確定した判定である
（`BD-312` の上流に保存の規範が 1 件も無いため、保存形式と読むと下位が上位に無い規範を発明したことになる）。

**したがってファイルの JSON トップレベルの形は正本のどの層にも決められていない。`SPEC-149` が明文で委譲している HOW である。**

### 2.3 採る形と、その理由

**採る形: 文書ファイルは束（`specification.json`）と同じ schema に適合する JSON object。**
`schema_version` と 7 層すべてのトップレベル配列を持ち、当該文書が属さない層の配列は空。

理由 3 点。**いずれも嘘テストか既存条文であり、実装コストでは選んでいない。**

1. **`ROOT-047` と字面で一致する。** 「`specification.json` は `.verify/doc/` の文書モデル**そのもの**」。
   束と文書ファイルの schema が同じなら、両者の差は**分割だけ**になり、束は文書ファイル群の同一層配列を連結したものと一致する。
   形が違うと「そのもの」が成り立たない。
2. **未宣言の key が自動的に閉じる。** `specification.schema.json` は `additionalProperties: false` を持つ。
   同じ schema に適合させれば、宣言されていない余剰 field は schema 不一致となり `DS-1645`（`E-SCAN-010`、error）で落ちる。**新しい診断コードを作らずに済む。**
3. **`schema_version` をファイルごとに持つ。** 読み手が未知の版を推測せず拒否できる（`DS-1645`）。
   版を 1 箇所へ集めると全ファイルの読取りがその 1 ファイルに依存し、`BD-058`「全員が編集する中央共有台帳を持たない」に反する。

**依頼が挙げた「ファイルが層を宣言する field」は置かない。** 層はノード id の接頭辞で機械的に定まり（`BD-318` / `SPEC-462`）、
層名の key はモデルの構造（束と同じ配列）であって層の宣言 field ではない。
派生できる値を独立の真実にしない。

> `P-003`（require）: ある事実を別の情報から決定論的に導出できる場合、その事実を複数箇所へ独立して記録し、手動同期を要求する構造を避ける。

**この `P-003` は、採った形に対する反証でもある。§7-6 に開示する。**
（初版は「`P-003` / `BD-160` 系の原則」と書いていたが、`BD-160` は「永続cacheを正典または検証入力として使用しない」であって
この原則の条文ではない。逐語照合で落とした。）

**7 層すべてを必須にするか、在る層だけにするか**は実装者が最初に当たる分岐なので、`statement` の中で明示する（在る層だけにすると schema 変更を伴い、束との同一性が崩れる）。

### 2.4 それでも嘘が通る経路が 1 本残る → `DS-1658`（導出）

**層名の配列と id 接頭辞は、schema では一致を強制できない。** `specification.schema.json` の `$defs/id` は
全層の接頭辞を 1 本の union パターンで受けるため、`{"spec": [{"id": "DES-999", …}]}` は schema に適合する。

これを受理すると、**配列で層を読む実装と id 接頭辞で層を読む実装（`BD-318`）が同じノードを別の層に置く。**
`ROOT-042`（辺は層をまたぐ参照）の下で辺の向きが実装ごとに変わり、
下位層のノードを上位層の配列へ入れれば、そこへ `derives_from` を張った下流ノードは**上流に根拠を持つように見える（偽のリンク）。**

**判定: 導出。** `SPEC-462`「上流文書は層ごとのトップレベル配列に分け、**層ごとに id 接頭辞を持つ**」の逐語がこの対応そのものを定めており、
新設する文は**その違反を受理しないことを明示するだけ**である。違反時の状態は `DS-1645`（`E-SCAN-010`）に載る。新しいコードは作らない。

## 4. 項目④ — 束と `.verify/doc/` の関係（登録） → **既決＋据え置き。新設しない。**

実装が必要とする入力・出力は、すべて既存条文から読める。

| 必要な事実 | 既存条文 |
|---|---|
| 束は変換・執筆のための形であり、登録時に文書単位のファイルへ分かれる | `ROOT-047`（description、H-2 で追記済み）＋ `ROOT-048` |
| 出力は `.verify/doc/` の文書ごと 1 JSON ファイル | `BD-323` / `BD-321` / `BD-319` |
| 取り込まれた上流成果物はノードとして登録され、subject hash と `derives_from` を持つ | `REQ-335` / `SPEC-148` |
| ノードは登録時の内容ハッシュを field として保持しない（hash は計算する） | `DES-573` / `DES-572` |
| id は採番し直さない | `DS-1637` |
| 入力フォーマットと登録方式そのものは下位へ委譲 | `REQ-309` / `SPEC-149` |

**「登録がノードの内容を書き換えない」を新設しない理由**: 書き換えれば `statement` が変わり、`DES-572` により subject hash が動く。
束縛していた判断記録・承認はその時点で失効する（`DS-1599` は `description` だけの変更が失効させないことの裏返し）。**嘘は通らず、fail-closed に倒れる。**

**据え置き**: どのコマンド／ツールが登録を行うかという操作面は Issue #14 が先送り済みであり、依頼の除外にも入っている。新設しない。
