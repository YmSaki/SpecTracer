### 8.2 依頼された 1 点の判定: **設定で免除できると、鎖の切れ目は隠せる。**

**隠せる。** 具体的に書く。

ある `REQ-` ノードの上流（`derives_from`）が削除され、祖先の辺にも覆われなくなったとする。
これは**鎖の切れ目そのもの**であり、`REQ-098`（「孤児文書…が生じる場合、状態は `MISMATCH`」）と
`REQ-089`（「`MISMATCH` の場合、受け取った者の行動はコードを触る前に宣言側（上流）を直すことである」）が想定している事象である。

`doc.roots` があると、**`config.yaml` に 1 行足すだけで、このノードは孤児でなくなる。**
ノードの id も、層も、`derives_from` も、subject hash も変わらない。
どの辺も切れず、どの判断記録・承認も失効しない（`DS-1614` は subject hash の変化にしか反応しない）。
**検証グラフのどこにも痕跡が残らないまま `orphan_detection` が `PASS` になる。**

これは Issue #11 F1 が守ろうとしている瞬間そのものである。宣言側（上流を壊した当人、あるいは AI）が、
自分が作った切れ目を告げる信号を、自分で消せる経路になっている。**軸 C に照らして不可。**

### 8.3 対置: `root` 層への所属で同じことはできないか（できない）

「では `root` 層へ移せば同じでは」という反論に、非対称がある。**これが判定の決め手である。**

ノードを `root` 層へ移すと、次がすべて同時に起きる。

1. **id が変わる**（`specification.schema.json` `$defs/id` の接頭辞が `ROOT-` になる）。
2. **型が変わる**。schema の `rootItem` は `derives_from` を **property として持たない**
   （schema の逐語: 「系の根なので derived_from を持たない唯一の層」）。
3. **そのノードを id で名指していた下流の辺がすべて切れる** → `E-SCAN-012`（`chain_integrity = MISMATCH`）。
4. **subject hash が変わる** → そのノードを依存 closure に含む判断記録・承認が失効する（`DS-1614`）。

つまり `root` 層への移動は**検証グラフの中に必ず現れ、代償を伴う**。
`doc.roots` への 1 行追加は**何も起こさない**。同じ「根の指定」でも、隠蔽に使えるのは後者だけである。

**この非対称が成り立つ範囲を、過大に読まないための境界（開示）。**
上の (3) と (4) は、**そのノードが下流から引用されていることに依存している。**
下流に 1 件も引用が無いノード（誰も `derives_from` で名指していない、宙に浮いた文）を `root` 層へ移した場合、
切れる辺は無く、失効する判断記録・承認も無い。**その 1 ケースに限っては、層による指定も無痕跡になる。**

それでも判定は動かない。理由は 2 つ。

1. **設定による指定は全ケースで無痕跡だが、層による指定が無痕跡になるのは「誰も依存していないノード」だけである。**
   引用されているノード（＝鎖の一部として実際に荷重がかかっているノード）については、非対称はそのまま成り立つ。
2. 誰も依存していないノードを頂点として宣言しても、**そこにぶら下がる鎖が無いので、隠される切れ目も無い。**
   VO も下流ノードもそのノードを通っていない。

**したがって §8.4 の判定はこの境界の外では成り立つが、「層へ移せば必ず痕跡が残る」とまでは言えない。** 導出が主張できるのはここまでである。

### 8.4 判定: **導出で決着する。`doc.roots` による除外は消す。**

導出（明文ではない。導出であることを明記する）:

1. `REQ-060` が要求しているのは「根として指定された文書は対象外」であって、**指定手段を設定ファイルに限定していない**。
2. `REQ-061` / `SPEC-060` / `SPEC-233` は指定方式を下位へ委譲している。**下位は 2 つの方式のどちらを採ってもよい。**
3. `REQ-059` / `SPEC-059` / `SPEC-291` / `SPEC-422` は既に「**`root` 層のノードを除き**」を持っている。
   `root` 層への所属は、正典データそれ自身から決定論的に読める指定である。
4. 軸 C（§8.2・§8.3）により、設定による指定は嘘を通し、層による指定は通さない。
5. **したがって委譲された「根の指定方式」の答えは `root` 層への所属であり、`config.yaml` の列挙ではない。**

**上流の書き換えは要らない。** `REQ-060` は真のまま（「根として指定された文書」= `root` 層のノード）。
`REQ-061` / `REQ-310` / `SPEC-060` / `SPEC-149` / `SPEC-233` の委譲も満たされる（下位が方式を決めた、というだけ）。
**直すのは detailed_spec 以下だけである。**

### 8.5 「プロジェクトごとに鎖の頂点を宣言する手段」は何か

依頼の後半への答え。**別の手段は要らない。`root` 層そのものが宣言手段である。**

- schema は `root` を 7 層のひとつとして持ち、`rootItem` だけが `derives_from` を持たない型として定義されている。
  したがって**どのプロジェクトの正典にも `root` 配列がある**（`ROOT-047`: `specification.json` は `.verify/doc/` の文書モデルそのもの）。

- 外部標準や社外の与件が頂点になる場合も、その旨を `statement` に書いた `root` ノードとして記録する。
  **設定に id を列挙するのではなく、頂点であることを正典に書く。**
