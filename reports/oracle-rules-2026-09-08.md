## 1. 件 1 — DA-001 の識別子扱い

### 1.1 上流の逐語

```
REQ-073  `oracle_presence` の問いは、宣言された「何の時にどうなる」の不成立を、Test の
         非成功として反映する装置が存在するか、である。
REQ-074  不成立が構造から証明できる — どんな宣言の下でも不成立を検出できない（失敗し得ない、
         または失敗が検証対象の振る舞いに依存しない）ことが構造から証明できる — 場合、`FAIL`。
REQ-075  照合装置の存在が決定論的に確認できる場合、この検査は成立側とする。
REQ-076  不成立が構造から証明できることも、照合装置の存在が決定論的に確認できることも、
         決定論的に言えない（解析不能等）場合、`UNKNOWN`。
REQ-077  静的解析の役割は不成立の証明である。
REQ-079  静的解析は成立の証明装置ではなく、証明できない場合は何も言わない。
REQ-080  証明の失敗は `UNKNOWN` の事由ではない。
REQ-081  照合内容が宣言の期待と意味的に一致するかは、本検査の主張に含めない。
REQ-082  意味の疑義は検査ではなくエスカレーションの領分である（→ §12）。
REQ-108  `UNKNOWN` をエラー処理のフォールバック先として使う実装は仕様違反である。
```

基本仕様（spec 層、`DS-606` が明示的に引く先）:

```
SPEC-066  oracle_presenceの問いは、宣言された「何の時にどうなる」の不成立を、Testの
          非成功として反映する装置が存在するかである。
SPEC-067  静的解析の役割は不成立の証明である。
SPEC-068  静的解析は成立の証明装置ではない。
SPEC-069  意味の疑義は検査ではなくエスカレーション（§11）の領分である。
```

`SPEC-067` / `SPEC-068` は `REQ-077` / `REQ-079` をそのまま降ろしたもので、`REQ-080` に相当する文は spec 層に無い。したがって `REQ-080` の「証明」の主語は `REQ-077`〜`REQ-079` の連なりが固定している **不成立の証明**である。

### 1.2 下流の逐語

```
DS-609  `oracle_presence`に動的な昇格経路は無い。
DS-610  静的解析は不成立の証明であり、証明の失敗は`UNKNOWN`であって、runtime証拠で
        `PASS`へ昇格しない。
DS-621  DA-001（定数アサーション）はoracle_presenceへ供給する検査であり、引数がすべて
        リテラル・定数式のassertを内容とし、関数内のassert相当がすべて定数アサーションで
        あることをFAIL条件とし、定数性を確定できない式をUNKNOWNへ退避する例とする。
```

（`DS-609` / `DS-610` はいずれも `derives_from: []`、source は 詳細設計 §7.1「判定の原則」L1018。）

### 1.3 判定 — DS-621 は正当な具体化、DS-610 が欠陥

**DS-621 は上流と矛盾しない。** 上流の 3 分岐と 1 対 1 に対応している。

| 上流 | DA-001 の対応 |
| --- | --- |
| `REQ-074` 不成立が構造から証明できる → `FAIL` | 関数内の assert 相当が**すべて**定数アサーション。定数アサーションは検証対象の振る舞いに依存せず失敗し得ないので、`REQ-074` の「失敗が検証対象の振る舞いに依存しない」に当たる |
| `REQ-075` 照合装置の存在が決定論的に確認できる → 成立側 | assert 相当のうち 1 つでも非定数であることが確定すれば、その assert は振る舞い次第で失敗しうる照合装置である |
| `REQ-076` いずれも決定論的に言えない → `UNKNOWN` | 「定数性を確定できない式を UNKNOWN へ退避」 |

`REQ-080`「証明の失敗は `UNKNOWN` の事由ではない」と `DS-621` の `UNKNOWN` 退避は衝突しない。`REQ-080` が禁じているのは、**解析が成功して `REQ-075` の成立側を確認できた場合に、なお「不成立を証明できなかった」ことを理由に `UNKNOWN` へ落とすこと**である。`DS-621` の退避事由は解析そのものが確定できない場合、すなわち `REQ-076` の「解析不能等」であって、`REQ-080` の禁止対象ではない。適用対象が違う。

**衝突しているのは `DS-610` である。** 同じ語で正面から逆を言っている。

| | 逐語 |
| --- | --- |
| `REQ-080`（require） | 証明の失敗は `UNKNOWN` の**事由ではない** |
| `DS-610`（detailed_spec） | 証明の失敗は `UNKNOWN` **であって** |

`DS-610` の読みを採ると、不成立を証明できなかった Test はすべて `UNKNOWN` になる。すると `REQ-075` の成立側経路が消え、`DS-606`「全ルールが違反なしなら `PASS`」に到達する Test が原理的に存在しなくなる。`DS-610` は `REQ-080` に反するだけでなく、`REQ-075` と `DS-606` を空にする。

層の権威は `require` > `detailed_spec` であり、`DS-610` は `derives_from` が空、すなわち上流に根拠を持たない詳細仕様の記述である。**詳細仕様側の欠陥として処理する。**

### 1.4 適用

`DS-610` を退役し、後継 `DS-1680` を置いた（commit `a861365`）。

```
DS-1680  静的解析は不成立の証明であり、不成立を証明できないことだけを理由に`UNKNOWN`とは
         しない。照合装置の存在が決定論的に確認できる場合は違反なしとし、不成立の証明も
         照合装置の存在の確認もいずれも決定論的に言えない場合に限り`UNKNOWN`とする。
```

3 文とも `REQ-077` / `REQ-075` / `REQ-076` の restate であり、上流に無い規範を足していない。

`DS-610` 後段の「runtime証拠で `PASS` へ昇格しない」は後継に持たせていない。**同じ節の直前 `DS-609`「`oracle_presence` に動的な昇格経路は無い」が既に担っている**ためで、規範を落としていない。`DS-609` は `oracle_presence` 全体に対する無条件の禁止であり、`DS-610` 後段より広い。

`derives_from` は前身と同じ `[]` のままにした。後継に辺を与えると「root 外で実効的上流が空」の件数が 269 から 268 へ動き、依頼の不変条件を破るためである。**なお `DS-1680` が上流に辺を持たないこと自体は、この節（`DS-600`〜`DS-605`、`DS-609` など）の既存ノードと同じ状態であり、本件で新たに作った孤児ではない。**

### 1.5 依頼が前提していた実装挙動は現在の tree では成り立たない

依頼は「実装は assert の引数が識別子（リテラルでない）→ `NoViolation`（PASS 側）としている」としていた。`crates/vtest-audit/src/lib.rs` の `rule_da001` / `ConstantContext::classify` を読んだ結果、**HEAD の実装はそうなっていない。**

`classify` は `Constant` / `Runtime` / `Unknown` の 3 値を返す。識別子（`Expr::Path`）は、

- 定数表に解決できれば、その定義式を再帰的に分類する（`const YES: bool = true;` は `Constant`）
- **解決できなければ `Constness::Unknown` を返す**

`Constness::Runtime`（＝ PASS 側）が出るのは、宣言 target の呼出が `TargetCallMatch::Proven` で確定した場合だけである。`rule_da001` は `saw_runtime` → `Pass`、そうでなく `saw_unknown` → `Unknown`、残りを `Fail` とする。**「識別子だからリテラルでない、ゆえに PASS」という枝は存在しない。**

つまり実装は `DS-621`・`REQ-076` の側に立っており、むしろ `REQ-075` が許す成立側より保守的である（宣言 target 以外の関数呼出に束縛された識別子は `Runtime` ではなく `Unknown` になる）。**保守側への寄りなので嘘の PASS は生まない**が、`DS-1680` の適用後は `REQ-075` の成立側をどこまで取るかが実装の裁量として残る。これは実装 PR の論点であり、正本の欠陥ではない。

**この節は正本の変更根拠には使っていない。** `DS-610` の退役は §1.3 の逐語だけで決まっており、実装の状態に依存しない。

### 1.6 埋めずに報告する穴 — DA-001 の識別子追跡の深さ

`DS-628`「DA-002 / DA-003 のデータフロー解析は関数内のローカル束縛の追跡（let束縛、メソッドチェーン、フィールドアクセス）までとする」と `DS-629`（クロージャ内・マクロ展開内は UNKNOWN）は、**明示的に DA-002 / DA-003 に限定されている**。DA-001 が識別子の定数性をどこまで辿ってよいかを定める記述は正本のどの層にも無い。

帰結: 同じ Test が、実装の追跡の深さ次第で `FAIL`（全部定数と確定）にも `UNKNOWN`（確定できず）にもなる。境界が正本に無いため、**実装が規範を発明する位置にある。**

`DS-628` を DA-001 へ広げる案は自然だが、それは**提案であって決定ではない**。DA-001 は「定数性」を、DA-002 / DA-003 は「呼出・結果の到達」を追う別の解析であり、同じ境界が妥当かは自明でない。ここでは規則を足さず、詳細仕様層の underspecification として報告するにとどめる。

## 2. 件 2 — DA-004（自己比較）と決定性テスト

### 2.1 逐語

```
DS-624  DA-004（自己比較）はoracle_presenceへ供給する検査であり、`assert_eq!(a, b)`でaとbが
        トークン列として同一であることを内容とし、該当assertが存在することをFAIL条件とし、
        UNKNOWNへ退避する例は無い（構文的に確定）。
```

依頼が挙げた具体例:

```rust
assert_eq!(hash_fn(&x), hash_fn(&x));
```

`DS-624` の逐語に逃げ道は無い。トークン列が同一なので `FAIL` になる。

### 2.2 2 つの読み

- **(a)** これは振る舞いの oracle ではない。`DS-624` どおり `FAIL` が正しい。
- **(b)** 決定性は正当な性質である。それを検証する Test を oracle 無しと扱うと、「決定性を検証している」という主張が `FAIL` になる。

**(a) を「純粋関数なら `f(x) == f(x)` は常に真だから」とは論証しない。** `f` が非決定的なら失敗しうるので、この式は決定性についての振る舞いの oracle として機能する。読み (b) の力はここにある。判定はこの点では決まらない。

### 2.3 判定 — 嘘が通るか

**読み (b) を採ると嘘が通る。** `assert_eq!(e, e)` の形をした assert は、次の 2 つを含む。

1. 決定性を意図して書かれたもの
2. 期待値を書き忘れた、あるいはコピー&ペーストで両辺が同じになった空虚な assert

**この 2 つは構文的に区別がつかない。区別するには書き手の意図を読む必要がある。** `REQ-081`「照合内容が宣言の期待と意味的に一致するかは、本検査の主張に含めない」と `REQ-082`「意味の疑義は検査ではなくエスカレーションの領分である」が、まさにその判断を本検査から排除している。読み (b) を採ると、2 の空虚な assert が「決定性テストだ」という自己申告だけで `PASS` を通る。これは F1（AI の完了宣言の受領時に嘘の PASS を止める）が守ろうとしている瞬間そのものである。

**読み (a) を採っても嘘は通らない。** `FAIL` は偽陰性（見逃し）ではなく偽陽性（過剰検出）を生む方向の誤りで、`PASS` を通さない。誤って `FAIL` にされた側は、書き手が気付いて対処できる。

### 2.4 決定性の主張は失われない

読み (a) の代償は見た目より小さい。**決定性の主張は `DS-624` に触れない形で書ける。**

```rust
let a = hash_fn(&x);
let b = hash_fn(&x);
assert_eq!(a, b);
```

`a` と `b` はトークン列として同一でないので `DA-004` は発火しない。`DA-001` も、`a` / `b` が `hash_fn` の呼出に束縛されたローカルであってリテラル・定数式ではないため、`DS-621` の `FAIL` 条件（関数内の assert 相当がすべて定数アサーション）を満たさない。`REQ-075` の照合装置として確認できれば成立側になる。**すなわち「決定性を検証している」という主張は、正本の下でそのまま表現でき、`oracle_presence` の `FAIL` を受けない。** 読み (b) が救おうとしていた検証能力は、実際には失われていない。

（§1.5 のとおり HEAD の実装は `hash_fn` が宣言 target でない場合この束縛を `Unknown` と分類するため、現状では `PASS` ではなく `UNKNOWN` になる。これは `DS-1680` 適用後の実装側の裁量の問題で、正本の側では成立側の経路が開いている。）

さらにこの書き方のほうが、決定性の検証として正確である。1 つの式の中で 2 回呼ぶ形は、評価順序と最適化に依存して「2 回呼ばれたこと」自体が保証されない。**2 回の呼出を別々の束縛にする形は、検証したい性質をより忠実に表す。**

### 2.5 適用

**正本の変更なし。`DS-624` は維持する。** Owner 裁定を要しない。上位（`REQ-081` / `REQ-082`）が本検査から意味判定を明示的に排除しており、そこから読み (a) が**導出できる**ためである。判定できない問いを Owner に上げるのではなく、上流の既決事項が答えを与えている。

### 2.6 dogfood 再現の確認

依頼の `assert_eq!(hash_fn(&x), hash_fn(&x))` に相当するものを探した。**追跡下の `*.rs` 全 27 ファイル**（`git ls-files '*.rs'`。`crates/` に加え `tests/fixtures/` を含む）を、複数行にまたがる呼出も拾えるよう括弧の対応を数えて `assert_eq!` の第 1・第 2 引数を空白除去のうえ突き合わせた。

トークン列同一の `assert_eq!` は 9 件見つかったが、**いずれも DA-004 自体を検査するための fixture / テストデータ**である（`crates/vtest-audit/src/lib.rs` 2 件、`crates/vtest-cli/tests/m3_acceptance.rs` 4 件、`crates/vtest-cli/tests/m7_acceptance.rs` 1 件、`tests/fixtures/calc/tests/calc_test.rs` 2 件）。`決定性` / `determinis` での探索でも、決定性を検証する production の Test は見つからなかった。

**依頼が挙げた dogfood のケースは、追跡下の tree には所在を特定できなかった。** 上の走査範囲で言えることはここまでで、未追跡ファイルや別ブランチについては何も言っていない。判定 §2.3–§2.4 はこの再現の有無に依存しない。
