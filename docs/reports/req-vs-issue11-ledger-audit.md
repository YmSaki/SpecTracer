## 1. 総括 — 収束点と解体点

**収束点（最重要）**: 受理済み最新の要件本文は既に台帳の方向を向いている。PR #9 が入れた新 §11「Testの検証成立性」（§11.1 条項1–2 / §11.2 条項3–4 / §11.3 不成立構造）と一般化された §16「検証対象の振る舞いの実現確認」は、台帳の `oracle_presence` と `target_binding` の**要件層の親としてほぼそのまま生存**する。§11.2 条項4（未確認と違反の区別）は F7 の UNKNOWN 側原則の要件層表現になっている。

**解体点は集中している**:

1. **§3 の設計思想**「各成果物間について、独立して一致・不一致を検証する」— F10 が 12 項目増殖の原因と診断したその思想そのもの（→ C-01）
2. **§17.2 の 12 項目表** — F8 が 4 検査に統廃合した対象の列挙（→ C-01）
3. **§6 / §12 の AI-as-judge** — システムが LLM 判定を検査結果として正式化する構造。F3/F4/F7/F8 と正面衝突（→ C-03）
4. **状態語彙** — NO_EVIDENCE が要件定義に不存在。MISSING / NOT_EXECUTED / NOT_CHECKED / STALE を検証状態として使用（→ C-02）
5. **吸収済み検査の形式残存** — §13 / §15 / §14 の独立検査形式。ただし §15 の規範意図（判定入力の変更で過去 PASS を引き継がない）は F5 のハッシュ束縛が実現形であり**意図は生存**（→ C-04）

## 3. 確定所見の詳細

### C-01 遷移ごと独立検査アーキテクチャ（12項目） [STATE_MACHINE / SCOPE_AGGREGATION]

- **要件定義側の証拠**: §3「これは単純な正典チェーンではない。各成果物間について、独立して一致・不一致を検証する」。§17.2 は Specification coverage 〜 Evidence validity の 12 項目 PASS を完全検証 OK の条件として列挙。§32 分解ツリーの 5（Deterministic Test Audit）/ 6（Semantic Test Audit）分岐、§33 概念フローも同構造。
- **台帳側の証拠**: F8（12項目の統廃合 → 4検査）、F10「全遷移の検査は同型…検査の種類は1つ (chain_integrity)。**段はリンクであって検査ではない**」。
- **最小反例**: チェーンに上流リンクを 1 段追加する（例: 基本仕様→詳細設計）。§3 思想に適合する実装は検査項目を 1 本増やす（12→13）。台帳適合の実装は chain_integrity のリンクが 1 本増えるだけで検査数は不変。同一実装が両方に適合することはできない。
- **帰結**: §17.2 の表・§32 ツリー・§33 フローは再導出で全面書き換え。生存する個別要求（リンクの双方向完全性、fail-closed 集約）はリンク規則・集約規則として chain_integrity 配下へ移る。
- **最上流の無効成果物**: §3 検証モデル（F10 自身が「12項目増殖の原因: 各遷移に1検査を割り当てる設計思想」と診断した箇所）。

### C-02 状態語彙 [STATE_MACHINE]

- **要件定義側の証拠**: P-002 が NOT_CHECKED / UNKNOWN / NOT_EXECUTED / MISSING / MISMATCH / FAIL / STALE の 7 値を列挙。§7.1「…対応するmanaged Test Entityが存在しない状態は`MISSING`とする」。§14 は PASS/FAIL/NOT_EXECUTED/UNKNOWN、§16 省略時 NOT_CHECKED、§17.2 NG 条件 7 値、§23 も同語彙。**NO_EVIDENCE は文書中に存在しない**。
- **台帳側の証拠**: F7「生存: PASS / FAIL / MISMATCH / NO_EVIDENCE / UNKNOWN」「降格(診断ラベル化): MISSING / NOT_EXECUTED / NOT_CHECKED / STALE ほか」。存在資格の基準は「受け取った者の行動が変わるか」。
- **最小反例**: adapter が発見した Test に管理宣言が無い。要件定義適合の実装は検証状態 `MISSING` を返す。台帳適合の実装は 5 状態のいずれか＋診断ラベル MISSING を返す（どの状態かは未裁定 → U-03）。同一事象への出力語彙が両立しない。
- **帰結**: 状態を使う全節（P-002/§7.1/§14/§16/§17.2/§23/§18/§19）の語彙差し替え。F7 の行動基準（PASS=マージ可 / FAIL=実装を直す / MISMATCH=宣言側を直す / NO_EVIDENCE=証拠を作れ / UNKNOWN=エスカレーション）を要件層に明文化する必要。
- **最上流の無効成果物**: P-002 の状態列挙（初出）。fail-closed 原則自体は生存（F5 が依存）。

### C-03 LLM 判定のシステム内検査化 [OWNERSHIP]

- **要件定義側の証拠**: §6「SpecificationからRequirementへの取り込み完全性、およびRequirementからVOへの分解・網羅性についてLLMを利用可能とする。両者は別の監査結果として保存し…」— 判定主体はシステム内の LLM 監査で、その結果が §17.2 の Specification coverage / VO coverage / VO decomposition PASS を構成する。§12「LLMによる意味監査を実施可能とする。…決定論的監査結果とAI監査結果は区別して保持・提示する」— VO↕Intent↕Code の同一性判定を検査として保存。
- **台帳側の証拠**: F3「『テスト仕様と実装の比較』という第3の検査は…幻だったと確定」、F4「『宣言されていない義務』を発見する知能は載せない。…発見者は外部」、F7「UNKNOWN → 決定論の限界。意味判定できる者へエスカレーション」、F8「semantic_audit → 検査ではなく UNKNOWN エスカレーションプロトコル」「vo_decomposition → 検査ではなく出力機能」。
- **最小反例**: VO と Test Code の意味乖離が疑われる Test。要件定義適合: システムが semantic audit FAIL を監査結果として保存し完全検証 NG。台帳適合: システムは意味を裁定せず UNKNOWN を返し外部へエスカレーション。裁定主体の所在（内 vs 外）が両立しない。
- **帰結**: §6/§12 は「システムの検査」から「外部の発見者/裁定者を可能にするデータ形態・エスカレーション経路」へ再定義。§32 ツリーの 6 分岐消滅。
- **未決の付随論点**: §6 後段の監査**記録**要求（判定理由の保存・根拠追跡・対応関係変化後の PASS 無効化）は、判定主体の外部化後も vtest 側の保存責務として生存させるか台帳は沈黙 → U-06。
- **最上流の無効成果物**: §6（AI-as-judge の初出）。

### C-04 吸収済み検査の形式残存（意図は生存） [IDENTITY_FRESHNESS]

- **要件定義側の証拠**: §13（impl_consistency 独立検査）、§14（実行結果識別、§17.2 の Test execution / Runtime result 2 項目）、§15（evidence_validity、STALE 状態）。
- **台帳側の証拠**: F5「鮮度は独立検査ではなく設計制約に吸収。STALE 検出ロジックは書かない」、F6「STALE は…診断ラベルに降格。検証結果としては証拠なしと同じ NO」、F8「evidence_validity / test_execution / impl_consistency → 執行済み」、F3「テスト合否の判定権威は cargo test に全面委譲」。
- **最小反例**: 証拠のハッシュが現在ソースと不一致。要件定義適合: Evidence validity 項目が STALE/FAIL を状態として出す。台帳適合: 証拠は「存在しないもの」→ 状態 NO_EVIDENCE + 診断ラベル STALE。出力が両立しない。
- **意図の生存**: §15 の規範文「Evidenceの判定結果を変えうるTestの意味、実行条件、対象実装、および実行可能状態が現在状態と一致することを確認できなければ、そのEvidenceを現在のPASSとして利用してはならない」は、F5 のハッシュ束縛の要件層の親としてそのまま生きる。§14「結果をVerification Evidenceとして利用できること」も cargo 委譲（消費のみ）と両立する。死ぬのは**独立検査という形式**と **STALE という状態**のみ。
- **最上流の無効成果物**: §17.2（検査項目としての正式化）。

## 4. 欠落（台帳が要求、要件層に無い）

### G-01 要求層の不在
F10 は Owner のチェーンを「要求 → 要件定義 → 基本仕様 → 詳細設計 → VO → (実装, テスト)」と確定したが、最上段の要求層は repo 内に文書として存在せず、F1（一次ユーザー=開発者自身、守る瞬間=AI の完了宣言受領時、救うもの=嘘の PASS を信じてマージすること、帰結=MCP は本体）と F9（v0.1 は順方向のみ・完成の防衛）は Issue #11 の中にしか無い。§1 の目的文は問題領域は述べるが一次場面を欠き、§28 は CLI/MCP を同格に置いて F1 の「MCP が本体」と乖離する。F11 の下では上流文書は `.verify/` 内でハッシュ束縛される必要があり、GitHub Issue のままではチェーン最上段ノードとして束縛できない。→ **U-01（最初の詰め議題）**

### G-02 文書レイヤー要件の不在
F11（総称ノード型 `document` = id + path + content_hash + 上流参照、リンクは derives_from 一種のみ、chain_integrity はリンク存在とハッシュ照合のみ・内容非関知、スコープ爆発 3 経路の明示拒否）と F12（文書レイヤーの孤児検出は v0.1）に対応する要求が要件定義に無い。§24 は入力候補の列挙のみ。なお §31 OOS-001（仕様書同士の品質監査はスコープ外）は F11 の内容非関知と**一致**しており生存。

### G-03 スコープ表明の不在
F9 の非関知宣言「v0.1 は宣言された義務の裏付けのみを検証し、宣言されていない実装の存在は関知しない」が §31 に無い（README 一行要求も未反映）。F2 の統合命題（過少実装と過実装は宣言量に対する過不足の両側 = 単一検査）の要求層表現も無い — v0.2 予告としても書かれていない。

### G-04 UNKNOWN 検疫の不在
F7「UNKNOWN ≠ エラー。正常動作としての降参。内部エラー・入力不正は exit code 2/3 の領分。UNKNOWN をフォールバック先として使う実装は仕様違反」に対応する要件が無い。§11.2 条項4 が「未確認と違反の区別」で片側を入れたが、エラーとの分離・フォールバック禁止は未表現。

# 追補: Owner 裁定 2026-08-24（判断と承認の分離）

decision / judgment と approval は別概念とする。

- **判断（Judgment）**: 対象について選択・判定を行うこと（PASS と判断する、A/B を選ぶ、どの要求を採用するか判断する等）。承認されていなくても存在・記録可能。フィールドは actor / subject / decision（必須）、reason / evidence（optional）。
- **承認（Approval）**: その判断または方針を「この内容で進める」と正式に認め、確定状態にすること。フィールドは approver / subject または judgment reference / approved state（必須）、reason（optional）。
- **判断済み ≠ 承認済み**。判断済みでも未承認なら承認済みより弱い。判断記録と承認記録を同一概念・同一 entity として扱わない。具体 schema は下位仕様へ委譲。

**修正**: §12 は外部判断とその記録を扱い、§19 は判断・方針の正式採用（承認）を扱う。「UNKNOWN の解消は承認（§19）として記録される」という同一視を解き、「UNKNOWN に対して判断できること」と「その判断が正式承認されること」を別段階として表現する。2026-08-24（記録要件）の actor/subject/decision 必須・理由 optional は**判断記録**への要件。承認記録も誰が・何を承認したかは追跡可能とするが、判断記録と同一 entity であることは要求しない。

# 追補: Owner 裁定 2026-08-24（検証状態・承認・フェーズゲートの分離）

1. **Verification State と Approval は別概念**。
2. 5状態（PASS/FAIL/MISMATCH/NO_EVIDENCE/UNKNOWN）は**検証結果のみ**を表し、承認状態を混入させない。
3. 技術的に PASS でも未承認である状態を許容する。
4. 未承認であることだけを理由に PASS を UNKNOWN 等へ変更しない。
5. 承認済みであることを理由に FAIL/MISMATCH/NO_EVIDENCE/UNKNOWN を PASS へ変更してはならない。
6. 判断（judgment=選択・判定）と承認（approval=正式確定）を分離（2026-08-24 判断/承認分離の再確認）。
7. Agent も承認権限を持ち得る。ただし全 Agent が承認権限を持つことは要求せず、一般作業 Agent が持つべきとも要求しない。
8. 誰がどの対象・範囲について承認可能か（approval authority）はプロジェクト側で定義可能。
9. フェーズ・工程・ゲートごとに、進行条件として必要な Verification State と Approval を定義できることが望ましい（例: 通常開発中=PASS で進行可・承認不要／Release gate=PASS + Reviewer 承認／Delivery gate=PASS + Owner/PM 承認）。具体的なフェーズ名・承認ロール・必要承認数・権限 schema は下位仕様へ委譲。

**反映**: §5.5（検証状態と承認の分離）新設、§19（Agent の承認権限・approval authority のプロジェクト定義）追記、§26.4（フェーズゲート進行条件）新設。
