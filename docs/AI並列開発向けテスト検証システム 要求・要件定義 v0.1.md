# AI並列開発向けテスト検証システム 要求・要件定義 v0.1

---

# 第I部 要求

本部の各行は、Issue #11（v0.1 凍結台帳）または Owner 裁定にトレースされる。本部と矛盾する要件・仕様・実装の変更は MISMATCH として扱う。

## R-1. 一次場面

- 一次ユーザーは開発者自身である。
- 守る瞬間は、**AI の完了宣言の受領時**である。
- 防ぐのは、**嘘の PASS を信じてマージすること**である。
- 帰結（導出）: MCP インターフェースは飾りではなく本体である。嘘はエージェントのループ内で止める。

## R-2. スコープ防衛

- v0.1 は順方向 — **宣言された義務の裏付けの検証** — のみで出荷する。
- v0.1 は宣言されていない実装の存在を関知しない。README に非関知宣言を一行入れる。
- 実装レイヤーの孤児検出（過実装検出）・シンボル列挙の定義・上流文書の意味構造は v0.2 へ送る。
- 選定理由: スコープ拡大は所有者の既知の悪癖であるため、完成の防衛を優先する。

## R-3. 言語・ツール非依存と拡張性

- 言語依存なし。
- テストツール依存なし。
- 言語とツールは拡張可能。
- どのバージョンで実現するかは指定しない。

## R-4. 対象環境（並列開発）

- 本システムは、複数の人間および複数の AI Agent が同時並行で開発する環境でも成立する。
- 最小構成は人間 1 人でもよいが、実利用では人間複数 + AI Agent 複数、場合によっては多数の AI Agent が並列に作業する環境を想定する。

## R-5. 途中導入可能性

- 本システムは、プロジェクト開始時から導入されていることを前提としない。既に開発途中または既存のプロジェクトへ、後から導入できる。
- 「既に大量のソースコードと Test が存在するプロジェクトを検証対象として扱える」ことは本要求の子とする（並列開発要求 R-4 からは導出しない）。

# 第II部 要件定義

## 1. 目的

本システムは、テストが存在して PASS しているという事実だけでは信用できない問題を解決する検証システムである。防ぐのは、AI の完了宣言を受け取った瞬間に、嘘の PASS を信じてマージしてしまう事故である（R-1）。

テストランナーが PASS と言った事実そのものは疑わない（→ §7 判定権威）。本システムが照合するのは、その PASS と宣言の間にある次の 4 点である。

1. そのテストは、宣言された義務（VO）と宣言鎖で繋がっているか
2. そのテストは、宣言された検証対象の振る舞いを実際に生じさせたか
3. そのテストは、宣言された不成立を自身の非成功として反映する装置を持つか
4. その証拠は、現在のコードに対するものか

この 4 点がすべて成立した場合のみ、完全検証においてその検証対象を OK とする。

本システムは、

> **「テストが通った」を検証するツールではなく、「そのテストを通ったという事実を信用してよいか」を宣言から実行結果まで追跡して検証するツール**

である。

---

## 2. 基本原則

### P-001 検証機であり修正方針決定機ではない

本システムは、宣言・Test・実装・証拠が食い違っている場合、その不一致を検出し、受け取った者が次に取るべき行動が一意に決まる状態（→ §5）で提示する。

本システム自身は、仕様が正しい・実装が正しい・テストが正しい・どれを修正すべきである、と決定してはならない。修正対象の選択は、本システムの外側にある開発者・レビュー担当・PM・AI Agent などが行う。

### P-002 Fail Closed

完全検証において、未検証は合格として扱わない。完全検証の OK は、要求されたすべての検査が `PASS` である場合に限る。`FAIL` / `MISMATCH` / `NO_EVIDENCE` / `UNKNOWN` のいずれか一つでもあれば OK にならない。

利用者が特定の検証観点だけを確認したい場合は、検証 scope を限定できる。scope 限定の結果を提示する場合も、実施しなかった検査を `PASS` へ変更してはならない。

### P-003 単一の正典を重複して持たない

ある事実を別の情報から決定論的に導出できる場合、その事実を複数箇所へ独立して記録し、手動同期を要求する構造を避ける。検索インデックス、グラフ、キャッシュなどの派生情報は、正となる情報から再構築可能でなければならない。

### P-004 AI の自由度を必要以上に与えない

既知の作業手順と既知の入力項目を持つ操作については、AI へ自然言語で自由に編集させる方式より、構造化された質問・入力・検証によって操作させる方式を優先する。この考え方を本プロジェクトでは **Agent Form Engineering** と呼称する。

### P-005 規範の伝播は上流→下流、逆はフィードバック

規範的な導出・変更伝播の方向は 要求 → 要件定義 → 基本仕様 → 詳細設計 → VO → Test の上流から下流とする。下流で不足・矛盾・疑義が見つかった場合、その情報は上流を再判断するための材料として逆方向へ提示できるが、下流成果物を根拠に上流成果物を自動的に書き換えてはならない。上流の変更が正式に確定した後、再び正方向に下流を追随させる。逆方向は「規範の伝播」ではなく「判断材料のフィードバック」である。

## 3. 検証モデル

### 3.1 Test 判定の主語

Test の判定の主語は、常に **宣言 + コード + 証拠の組** である。裸のテスト関数は判定対象ではない。「何のためのテストか・何を検証するか・何がどうなれば OK か」に答えを持たないテストは、本システムに管理対象として存在できない（宣言を欠く発見テストの扱いは §5.3）。

### 3.2 宣言鎖

宣言は次の鎖をなす。

```text
document（上流文書）
      | derives_from
      v
document（下流文書）
      | derives_from
      v
Verification Obligation (VO)
      |
      v
Test（covers 宣言）
```

- 上流文書はすべて単一の総称ノード型 `document`（id + path + content_hash + 上流参照）で表現する。文書間のリンクは `derives_from` の一種のみとする。各リンクは §3.4 の任意説明（optional な導出理由）を保持できる。
- VO は 1 件以上の `document` から derives_from で導出される。VO と文書の間に他のエンティティ層を置かない。
- 文書層の段数は総称的に設計し、**リンクを追加してもスキーマが壊れないこと**を設計制約とする。段はリンクであって検査ではない。
- 本システムは文書内容の意味的な良し悪しに関知しない。文書種別ごとの専用スキーマ・文書間リンクの意味論の増殖・文書内容の良否検証を行わない。

### 3.3 検査

検証は次章の **4 検査のみ** で行う。鎖に段（リンク）が増えても検査は増えない。

### 3.4 関係型とトレーサビリティ

- **関係型を単一へ潰さない。** 文書間は derives_from、VO → Test は covers、Test ↔ 実装は検証対象 / 実装 traceability のように、性質の異なる関係は区別してよい。重要なのは、それらを横断してトレース可能であることである。関係型そのものを意味論的に増殖させることは求めない。
- **契約上必須のリンクは必須、任意関係は欠落可、説明文は任意。** 各関係のうち契約上必須と定義されたリンク（`parent --relation--> child`）は必須とする。任意（optional）と定義された関係（例: §9.3 の実装 traceability）は欠落してよい。存在するリンクに付す「なぜこの子がこの親から導出されたか」という説明文・導出理由は任意（optional）とし、空でも chain_integrity 違反・`MISMATCH` としてはならない。ただし説明文を付加・保存できるデータ構造とする。
- **任意ノードからのトレーサビリティ取得。** 最小の意味単位「上流ノード → 関係 → 下流ノード」を任意のノードから取得できる。さらに必要に応じて上流／下流へ連続して辿れ、プロジェクト全体のトレーサビリティ構造も取得できる。常に全チェーンを表示することは求めない。
- **役割ごとの参照観点。** 同一のトレーサビリティ構造から、利用者の役割または利用目的に応じて参照対象・関係・集約粒度を変えた projection を取得・提示できる（例: PM は上位の要求・要件・仕様・VO の状態と未確定/NG、Tester は VO・Test・検証対象・Evidence・未実施/失敗理由、Coder は実装から関連 Test・VO・上流仕様へのトレース）。役割を固定 enum やモード名として仕様化することは本要件に含めず、preset・UI・モード体系は下位仕様へ委譲する。

## 4. 検査

各検査は一つの問いを持ち、複数の証拠源で答えてよい。答えは検証方法・実行形態に依らず同一でなければならない（§8 条項 3）。

### 4.1 chain_integrity — 宣言鎖の完全性

**問い: 宣言鎖のすべてのリンクが存在し、ハッシュ照合が成立するか。**

- 文書層: 各 `document` の derives_from 参照先が存在し、content_hash が現物と一致すること。
- VO 層: 各 VO が 1 件以上の `document` への解決可能な derives_from を持つこと。
- Test 層: 発見された各 Test に対応する管理宣言（構文上有効な Test ID・1 件以上の `covers`・その他の必須 metadata）がちょうど 1 件存在し、`covers` の全 VO 参照を解決でき、Test ID が発見結果全体で一意であること。
- leaf VO から Test への方向（検証実装の存在）と、発見された Test から宣言への方向（管理宣言の解決）の両方が成立して初めて、宣言鎖の双方向完全性が成立する。
- どのリンクで切れたかは診断ラベルで示す。

すべての Test を管理対象とすることと、当該 Test を仕様適合の証拠として算入することは、別個の条件とする（→ §8）。

### 4.2 orphan_detection — 文書層の孤児検出

**問い: 親を持たない `document` ノードが存在するか。**

- 根として指定された文書は対象外とする。根の指定方式は基本仕様で定める。
- 対象は文書層のみとする。実装レイヤーの孤児検出（宣言されていない実装の検出）は行わない（R-2）。

### 4.3 target_binding — 宣言対象の振る舞いの実現

**問い: その Test が検証対象とする振る舞いが実際に生じ、その振る舞いを反映した観測が得られたか。**

- Test がテストランナー上で PASS しても、検証対象とする振る舞いを実際には生じさせていない場合、その Test を完全検証済み OK としない。
- 一つの問いに対して静的解析と動的計測の 2 つの証拠源を持つ。静的に確定できなければ `UNKNOWN` とし、動的証拠で昇格できる。
- 実装 construct（Source Target）を検証対象とする実行形態では、宣言された対象コードが実際に Test 実行経路へ入ったことをこの確認方法とする。複数 target を宣言した Test では各 target の実行を個別に計測し、1 件でも実行回数が 0 なら `FAIL`（診断: NOT_EXECUTED）、1 件でも解析不能でかつ `FAIL` がなければ `UNKNOWN`、全 target の実行を確認できた場合だけ `PASS` とする。
- 他の実行形態における確認方法は、§8 条項 3 に従い、当該形態に適した方法として下位仕様で定める。特定の実行形態の確認方法を、別の実行形態の Test へ一律に要求してはならない。
- この検査は完全検証モードではデフォルトで有効とし、高速な限定 scope の検証では省略可能とする（省略時の扱いは §5.3）。

### 4.4 oracle_presence — 照合装置の存在

**問い: 宣言された「何の時にどうなる」の不成立を、Test の非成功として反映する装置が存在するか。**

出力は次で定まる。

1. 不成立が構造から証明できる — どんな宣言の下でも不成立を検出できない（失敗し得ない、または失敗が検証対象の振る舞いに依存しない）ことが構造から証明できる — 場合、`FAIL`。
2. 照合装置の存在が決定論的に確認できる場合、この検査は成立側とする。
3. どちらも決定論的に言えない（解析不能等）場合、`UNKNOWN`。

- 静的解析の役割は**不成立の証明**である。成立条件から明確に外れる Test を決定論的に検出し、外部監査へ送る前に拒否する（§8）。静的解析は成立の証明装置ではなく、証明できない場合は何も言わない。証明の失敗は `UNKNOWN` の事由ではない。
- 照合内容が宣言の期待と意味的に一致するかは、本検査の主張に含めない。意味の疑義は検査ではなくエスカレーションの領分である（→ §12）。
- 答えは assert の所在・実行形態（内部 construct 検証か境界の振る舞い検証か）に依らず同一でなければならない。実行形態別の判定規則を設けない。

## 5. 検証状態

### 5.1 状態は 5 つ

検証状態は次の 5 つのみとする。状態の存在資格は「**受け取った者（人間/エージェント）の行動が変わるか**」であり、意味の違いは資格にならない。

| 状態 | 受け取った者の行動 |
|---|---|
| `PASS` | マージ可 |
| `FAIL` | 実装（テスト実装を含む）を直す |
| `MISMATCH` | コードを触る前に宣言側（上流）を直す |
| `NO_EVIDENCE` | 証拠を作る（機械的に解決可能） |
| `UNKNOWN` | 決定論の限界。意味判定できる者へエスカレーションする |

### 5.2 診断ラベル

`MISSING` / `NOT_EXECUTED` / `NOT_CHECKED` / `STALE` などは、状態に付随して原因を説明する**診断ラベル**であり、検証状態ではない。診断ラベルの語彙は下位仕様で定める。

### 5.3 状態の割当

| 事象 | 状態 | 診断ラベル |
|---|---|---|
| 発見された Test に管理宣言が無い | `MISMATCH` | MISSING |
| `covers` の VO 参照を解決できない / 同一 construct から複数 entity / Test ID 衝突 | `MISMATCH` | — |
| 文書鎖のリンク切れ / content_hash 不一致 / 孤児文書 | `MISMATCH` | STALE 等 |
| 証拠が存在しない / 証拠のハッシュが現在の対象と不一致 | `NO_EVIDENCE` | STALE 等 |
| scope 限定により検査を実施しなかった項目（完全検証の集約時） | `NO_EVIDENCE` | NOT_CHECKED |
| discovery が不完全 / 解析不能 | `UNKNOWN` | — |
| テストランナーが失敗を報告 | `FAIL` | — |
| 宣言された検証対象の実行が 0 回 | `FAIL` | NOT_EXECUTED |

### 5.4 UNKNOWN の検疫

`UNKNOWN` はエラーではない。**正常動作としての降参**である。内部エラー・入力不正は検証状態と別系統（終了コード）で表現し、その体系は下位仕様で定める。`UNKNOWN` をエラー処理のフォールバック先として使う実装は仕様違反である。

### 5.5 検証状態と承認の分離

検証状態（§5.1 の 5 状態）は検証結果のみを表し、承認状態を混入させない。承認（§19）は検証状態と独立した別軸である。

- 技術的に `PASS` であっても未承認である状態を許容する。
- 未承認であることだけを理由に `PASS` を `UNKNOWN` 等へ変更してはならない。
- 承認済みであることを理由に `FAIL` / `MISMATCH` / `NO_EVIDENCE` / `UNKNOWN` を `PASS` へ変更してはならない。

フェーズ進行に承認を要するかは、検証状態と承認の組合せとして §26.4 のゲート条件で扱う。

## 6. 証拠

- 証拠は検証対象の**内容ハッシュに束縛**される。現在のソースのハッシュと一致しない証拠は、検証時に「存在しないもの」として扱う（`NO_EVIDENCE`）。
- 証拠ストアはハッシュキーを必須とする。
- Evidence の判定結果を変えうる Test の意味、実行条件、対象実装、および実行可能状態が現在状態と一致することを確認できなければ、その Evidence を現在の `PASS` として利用してはならない。この要求はハッシュ束縛によって設計制約として満たす。鮮度の独立検査は設けず、鮮度喪失は診断ラベル（STALE）として説明する。

---

## 7. 判定権威

テスト合否の判定権威は、当該 adapter のテストランナーにある。本システムは合否を判定せず、テストランナーの結果を証拠として消費する。実行の起動は本システムから行ってよいが、判定はしない。rust-cargo adapter における判定権威は cargo test である。

---

## 8. Test の検証成立性

### 8.1 Test の成立と証拠への算入

管理対象となる Test は、その宣言された目的に対して、検証対象の振る舞いを反映した観測に基づく有効な成否判定を持たなければならない。

そのうえで、仕様適合性の証拠として算入する Test は、その検証成立性が確認済みでなければならない。Test として成立しているかの検査と、仕様適合性の証拠として算入するかの判定は独立である。

この成立性の必要条件として、以下を要求する。

1. **検証成立性**: Test は、検証対象の振る舞いを反映した結果・状態・その他の観測に基づいて期待条件への適合と不適合を識別し、不適合が Test の非成功として反映されるものでなければならない。
2. **依存要素の信頼性**: Test の成否判定が他の構成要素の判定能力に依存する場合、その依存要素について正当性が確認されるか、検証基盤として明示的に信頼されていなければ、当該 Test の検証成立性を確認済みとして扱ってはならない。判定能力を担う依存要素は、正当性確認対象または明示的な信頼基盤として識別可能であり、成立性確認はそのいずれかで終端しなければならない。

### 8.2 成立性確認の原則

3. **証明方法への非依存**: 成立条件の確認方法は、検証対象、実行形態、観測方法に応じて異なってよい。特定の実行形態に固有の確認方法を、別の実行形態へ一律に要求してはならない。成立性の問いへの答えは、確認方法に依らず同一でなければならない。
4. **未確認と違反の区別**: 成立条件を確認できないことと、成立条件に違反していることを区別しなければならない。確認不能であることだけを根拠として違反を推定してはならず、成立確認済みとして扱ってもならない。

成立条件から明確に外れる Test は、可能な限り決定論的な解析によって検出する。決定論的解析で明確に不成立とできる Test は、外部監査・エスカレーションへ送る前に拒否可能であること。

### 8.3 決定論的に検出可能な不成立構造

以下は、§8.1 の成立条件を満たさないことを、**宣言の中身に依らず**決定論的に検出できる具体例である。いずれも「どんな宣言の下でも不成立を検出できない」ことが構造から証明できる。code fragment は Rust による例示であり、共通契約が Rust 構文を要求するものではない（R-3）。各 adapter は対応する言語・runner の構造に対して決定論的に判定できる範囲を提供する。

例示の前提となる宣言:

```text
VO-EX-001: parse_u32 は不正な 10 進文字列に対して Err を返す
Test 宣言: covers = [VO-EX-001], 検証対象 = parse_u32
```

失敗し得ない — 成否判定が定数である。

```rust
#[test]
fn rejects_invalid_decimal() {
    parse_u32("12a");
    assert!(true);
}
```

検証対象の振る舞いを生じさせるだけで、その観測を成否判定に利用していない。

```rust
#[test]
fn rejects_invalid_decimal() {
    parse_u32("12a");
    let x = 1 + 1;
    assert_eq!(x, 2);
}
```

観測同士の自己比較であり、成否が検証対象の振る舞いに依存しない。

```rust
#[test]
fn rejects_invalid_decimal() {
    let r = parse_u32("12a");
    assert_eq!(r, r);
}
```

その他、同様に Test の成否判定が検証対象の振る舞いを反映した観測に依存しない構造。

## 9. 検証対象と Source Target

### 9.1 検証対象

すべての管理対象 Test は、1 件以上の検証対象を宣言できなければならない。検証対象は、その Test が検証成立性（§8）を証明しようとする対象 — 宣言された「何の時にどうなる」の主語 — であり、実装 construct そのものに限定しない。外部から観測可能な契約・境界上の振る舞いも検証対象にできる。

実装 construct（Source Target）を直接検証する実行形態では、Source Target 宣言をそのまま検証対象の宣言として扱い、同一対象の二重宣言を要求しない。外部契約・境界上の振る舞いを検証する実行形態では、その契約または振る舞いを検証対象とし、内部 Source Target の宣言を Test 成立性の必須条件としない。

### 9.2 Source Target の識別

実装コード上の implementation construct を、Source Target として識別可能でなければならない。

- 1 つの Test は 1 件以上の Source Target を宣言できる。複数 target を宣言した場合も、各 target を独立に識別し、代表 1 件へ縮約してはならない。
- ソースコード自体への恒久 ID 埋め込みは必須としない。各 adapter は、Source Target を一意に解決でき、同一の source state から決定論的に正規化できる Target Reference を提供する。Target Reference の具体的な構文、namespace、symbol 種別は下位仕様へ委譲し、共通契約が path、module、function 等の特定言語構造を必須としてはならない（R-3）。
- 恒久 SRC ID を使用する場合、その ID は adapter 境界を越えて repository 全体で一意でなければならない。同一 SRC ID を複数 adapter または複数 Source Target が宣言した状態を曖昧な参照として受理してはならない。

### 9.3 実装 traceability

検証対象とは別に、Test または検証対象から、関連する Source Target への traceability を保持できる。この traceability は任意であり、影響分析・逆引き等に利用できるが、その存在自体を Test 成立性の条件としてはならない。traceability は関連付けであって、実装対応の証明ではない。検証対象と実装 traceability は別の関係として扱い、一方から他方を推定してはならない。

Source Target との関係（検証対象または traceability）を持つ Test について、Test から Source を検索でき、Source から関連 Test を逆引きできること。

## 10. Verification Obligation

### 10.1 定義

Verification Obligation（VO）は、

> 独立して「この条件が成立するか」と検証可能な仕様上の命題

とする。VO の粒度を、assert 文・test function・テストファイルなどのコード構文によって決定してはならない。

### 10.2 VO 分解

仕様は、テストによって十分な網羅性を確認できる単位まで VO へ分解**できる**こと。本システムは分解を表現・保持するデータモデルを提供する。分解が十分かの判定は本システムの検査ではない（→ §12）。

### 10.3 VO 階層

VO は階層構造を持つことができる。初回登録時に階層化されていることを必須とはしない。flat な VO 群と階層化された VO 群の両方を扱い、flat な VO を再帰分解または階層化する操作を提供する。

### 10.4 VO と Test の対応

VO と Test は 1:1 に限定しない。`1 VO -> 1 Test` / `1 VO -> N Tests` / `N VOs -> 1 Test` / `N VOs -> M Tests` を許容する。Test は VO の検証実装単位であり、VO そのものではない。Test を構成する言語構文や test runner 上の実行単位は adapter が識別する。

---

## 11. 検証空間の表現

- 仕様から必要な場合、同値 partition・境界値 partition を表現できることが望ましい。すべての VO へ明示的な partition 定義を要求しない。
- 複数の検証軸が存在する場合、その組合せ空間（全直積または軸単位）を表現できること。何をもって十分とするかは仕様・検証理由によって決定され、その判定は本システムの検査ではない（→ §12）。
- 複数の観点を同時に確認する Test が存在することだけを理由として、各観点を独立に証明したことにはしない。各観点の独立検証、または必要と定義された組合せ空間の検証のいずれかを表現・確認できること。

---

## 12. 発見・意味判定のエスカレーション

本システムは、宣言されていない義務・網羅漏れ・宣言と実装の意味のずれを、自ら発見・裁定しない。発見者・裁定者は外部（人間またはエージェント）である。

本システムの責務は次の 3 つである。

1. **データ形態の提供**: 外部の発見者が判断できる構造化出力（要求該当箇所と対応概念のペア、宣言鎖と検査結果、対象外とした範囲）を提供する。
2. **エスカレーション**: 機械が決定論で確定できない疑義は `UNKNOWN` として、意味判定できる者へ引き渡す。
3. **判断の記録と再検証**: UNKNOWN に対して外部（人間または判断可能 Agent）が判断できる。判断はその時点の対象成果物・前提状態に対して、依存 closure（ハッシュ）とともに記録される。判断が正式に採用されるか（承認）は §19 の別段階であり、判断済みと承認済みは区別する（判断済み ≠ 承認済み）。仕様・VO・Test 等が変更された場合、過去の判断を現在状態へそのまま流用してはならず、現在状態に対して通常の検証を再実施する。その結果は `PASS` / `FAIL` / `MISMATCH` / `NO_EVIDENCE` / `UNKNOWN` のいずれにもなり得る。変更そのものが `UNKNOWN` を生成するのではない。

判断の記録は少なくとも「誰が（actor）」「何を（subject）」「どう判断したか（decision）」を必須項目とし、追跡可能でなければならない。判断の理由・根拠・evidence note（根拠となった宣言、対象外とした範囲、具体例等）は任意（optional）とし、保存できる構造とする。理由が空であることだけを根拠に、その判断を無効・`UNKNOWN`・`NO_EVIDENCE`・`MISMATCH` 等として扱ってはならない。

---

## 13. Test Registry

各 Test は安定した Test ID によって識別可能であること。Test ID をハンドルとして、Test Intent・covers（VO 参照）・検証対象・Source Target・Location・監査記録・Execution Evidence を検索可能とする。

登録 adapter が Test として発見した実行可能な test construct は、すべて管理対象でなければならない。発見された Test 集合を `D`、構造上完全な managed Test Entity 集合を `M` とする。構造上完全とは、source declaration から構文上有効な Test ID、1 件以上の `covers`、その他の必須 metadata を Test Entity として具体化できることをいう。Discovered Test と entity の対応数は構造完全性に含めず、独立した整合性条件とする。`M` は VO 参照の解決と Test ID の大局的一意性を検査する前の集合とし、解決不能な `covers` を持つ entity や、他の entity と Test ID が衝突する entity も含む。

完全検証では次を要求する。

```text
∀ d ∈ D:
  d に対応する managed Test Entity がちょうど 1 件存在する
  and managed Test Entity.covers は 1 件以上である
  and covers の全 VO 参照を解決できる
  and Test ID が発見結果全体で一意である
```

これらの違反時の状態は §5.3 に従う。いずれも完全検証の `PASS` として扱ってはならない。

---

## 14. Test Intent

Test には、その実装コードだけを読まなくても、何を検証するか・どの VO に対応するか・何を入力条件とするか・何を期待するかを判断できる情報を関連付けられること。Test Intent は Test Entity の付随情報であり、宣言鎖のノードではない。具体的入力値を Test Intent または VO へ含めることを許容するが、必須とはしない。

---

## 15. Parameterized / Table-Driven Test

table-driven の論理形式を正式に許容する。adapter が識別した table-driven test construct 全体を一つの Test として登録でき、内部の各 case を独立 Test ID へ分解することを必須とはしない。必要な場合、cases 集合が VO に必要な入力空間を十分に代表または網羅しているかは、§12 の発見・判定の対象とする。code fragment の具体構文は adapter の言語・runner に従う（R-3）。

---

## 16. Structured Test Operation

Test 操作の公式経路として、Test ID または adapter が識別可能な Test construct を対象とした構造化操作（Create / Edit / Query / Audit）を提供する。Test 変更時には、対象・何を検証するか・VO・入力条件・期待結果などの既知項目を構造化入力でき、入力内容は可能な限りその場で検証する（例: 対象 symbol 不在、Test ID 不在、参照 VO 不在）。

- 公式 Test Edit 操作では、一回の操作対象を原則として一つの Test とする。暗黙に他の Test まで変更することを許可しない。Test 外部の通常ソースコード、helper、fixture 等の編集は Test Edit の責務としない。
- 通常の write/edit ツールや人間による直接ソース編集そのものは完全禁止しない。公式経路の提供によって誤編集・更新忘れ・複数 Test 同時変更の事故を低減し、直接編集による不整合も検証で検出可能であることが望ましい。

---

## 17. 途中導入と既存プロジェクト対応

本システムは、プロジェクト開始時からの導入を前提としない（R-5）。開発途中または既存のプロジェクトへ、後から導入できる。

### 17.1 既存資産の可視化

既に大量のソースコードと Test が存在するプロジェクトを検証対象として扱えなければならない。既存の文書・Source・Test を読み取り、VO の存在状況・既存 Test と VO の対応・Test の不足・検証成立性・宣言との不一致をそれぞれ可視化できること。VO が確定していない範囲を含むプロジェクトも読み取れること。未登録 Test、欠落する宣言、未確定の VO、未実施の検査または実行を検証済みとして扱ってはならない（状態は §5.3 に従う）。

### 17.2 導入時の責務境界

決定論的に処理可能な作業について、人間による反復的な手入力を必須としない。一方、要求・要件・仕様・VO 等の意味上の定義や対応関係を決定する責任は、プロジェクト側（開発者・設計者・PM 等）にある。本システムが「この文章は要求である」「この要求からこの要件を作るべき」「この Test は意味的にこの VO に対応する」といった意味判断・候補生成を行うことを、必須要件としてはならない。外部 AI / Agent による補助・提案は許容するが、その能力を検証成立条件にしてはならない。

### 17.3 判断待ち情報の構造化

導入時・検証時に生じる、未確定事項・不整合・未検証事項・機械的に確認済みの事実・外部判断が必要な事項を、機械可読な構造として保持・取得可能とする。表示形式（表・GUI 等）は要件でなく、下位仕様に委ねる。

### 17.4 導入難度の規模非依存（設計原則）

プロジェクト規模が大きいこと自体とは別の理由によって、導入難度が構造的に増大する設計を避ける。これは強い不変条件ではなく設計原則とする。コード量・Test 数・判断対象数など単純な物量増加に伴う処理量・作業量の増加は許容し、関係者との合意形成等は本原則の対象外とする。

---

## 18. 仕様入力（文書層）

仕様ソースとして、ソースコードより上流に位置する成果物を利用可能とする（要件定義・基本仕様・詳細設計・API Schema・Protocol Specification・型/データ仕様・DB schema・その他の機械可読仕様）。取り込まれた上流成果物は §3.2 の `document` ノードとして登録され、content_hash と derives_from を持つ。

対象ソースコード内の doc comment を、その対象実装自身の正当性を証明する唯一の仕様根拠として使用することは想定しない。

## 19. 承認

承認とは、判断（§12 の判断記録を含む）または方針を「この内容で進める」と正式に認め、確定状態にすることである。判断済みと承認済みは区別し（判断済み ≠ 承認済み）、未承認の判断は承認済みより弱い。VO 等の検証成果物について、確定・承認状態を表現可能とする。

- 承認は、対象または参照する判断（judgment reference）に承認済み状態を与える。§12 の UNKNOWN 判断も承認の対象になり得るが、判断できることと正式承認されることは別段階である。
- 承認は対象自身の内容だけでなく、承認判断が依存する上流文書・上位 VO の現在の依存 closure へ束縛する。対象またはいずれかの依存成果物が変更された承認を、現在の承認済み状態として利用してはならない。変更後は現在状態に対して検証を再実施し、その結果（§12 の 5 状態のいずれか）に従う。依存 closure またはハッシュを欠く承認を推測で有効化してはならない。
- 承認記録は「誰が（approver）」「何を（subject または judgment reference）」「どの承認状態か（approved state）」を必須項目として追跡可能とし、承認の根拠は任意（optional）に記録できる。承認記録は §12 の判断記録と同一 entity であることを要求しない。
- 承認主体を人間に限定しない。Agent も承認権限を持ち得る（Human / Verification Agent / Reviewer Agent / PM Agent 等）。ただし全 Agent が承認権限を持つことは要求せず、一般作業 Agent が承認権限を持つべきとも要求しない。
- 誰がどの対象・範囲について承認できるか（approval authority）は、プロジェクト側で定義可能とする。具体的な承認ロール・必要承認数・権限 schema は下位仕様へ委譲する。

## 20. 利用者

- **Coder AI**: 自身の変更が要求された検証を満たしたか確認する。
- **Developer**: Test の作成・変更・検索・検証を行う。
- **CI**: 同一条件で検証を再実行し、再現性を確認する。
- **Reviewer AI**: Coder の提出した Evidence と自身の再検証結果を照合する。
- **PM / PM Agent**: 上位単位から、必要な VO・Test の存在と現在の NG 箇所を確認する。

## 21. 対応範囲と adapter 境界

- 検証契約・ID・ハッシュ・Evidence・状態・集約の概念モデルは、言語および test runner に依存しない（R-3）。
- source discovery、決定論的解析、Structured Test Operation、test runner 起動、coverage 計測は adapter の能力として提供される。共通契約は特定言語の構文・構造を必須としない。
- core verifier を変更せずに別 adapter を登録できる境界を要求する。adapter の追加によって共通契約・スキーマが壊れないことを設計制約とする（R-3）。
- 組込 production adapter は `rust-cargo` とし、Rust・Rust function unit test・小規模な integration test を対象とする。`rust-cargo` 以外の production language adapter は v0.1 の提供範囲に含めない（R-2）。
- adapter が未登録、能力不足、または解析不能の場合、検証結果を推測で `PASS` へ昇格してはならない。能力不足で確認できない項目は §8 条項 4 に従い扱う。

---

## 22. インターフェース

主要インターフェースとして、AI Agent 向け MCP interface と CLI を提供する。MCP は本体である — 検証は AI エージェントの作業ループ内、完了宣言のその場で呼ばれる（R-1）。CLI・CI は同じ検証の別入口である。GUI は必須要件としない。

---

## 23. 並列 AI 開発への要求

多数の AI Agent が並列で Test を追加・変更することを前提とする。不必要に単一共有台帳へ書き込ませない・一つの Test 操作が他 Test へ波及しにくい・Test ID 衝突を検出できる・dangling reference を検出できる・semantic conflict を検出可能にする・派生 index を再構築可能にする・Test と関連情報の同期を人間/Agent の記憶だけに依存させない。具体的な保存形式や競合回避方式は基本仕様で決定する。

---

## 24. 非機能要求

- **NFR-001 並列性**: 複数 AI Agent による並列変更に耐えられること。
- **NFR-002 再現性**: CI 等により同一 revision・同一検証条件で結果を再現可能であること。
- **NFR-003 追跡可能性**: 文書から VO、VO から Test、Test から Source、Source から Test、Test から Execution Evidence まで追跡可能であること（任意ノードからの取得・遡行・全体構造は §3.4）。
- **NFR-004 再構築可能性**: 検索 index 等の派生データを正典から再構築可能であること。
- **NFR-005 Fail Closed**: 検証されていない事実を推測によって `PASS` としないこと。
- **NFR-006 説明可能性**: 検証結果について、結論だけでなく根拠（どのリンク・どの証拠・どの診断か）を提示可能であること。
- **NFR-007 自動化適性**: AI Agent、CI、CLI 等から非対話的に利用可能であること。
- **NFR-008 人間可読性**: 人間が VO・Test の不足、不一致、NG 理由を一覧で理解可能であること。

## 25. スコープ外

- **OOS-001 仕様書同士の品質監査**: 複数仕様成果物同士の文章上・意味上の矛盾を発見すること（文書層は §3.2 の通りリンクとハッシュのみを扱う）。
- **OOS-002 修正方針決定**: 不一致の場合にどれを正としてどれを変更するべきか判断すること。
- **OOS-003 通常ソースコード編集管理**: Test Edit 対象外の一般的な編集そのものを管理すること。
- **OOS-004 開発プロセス全体の管理**: PM、実装、レビュー等の開発工程自体を本システム内部で管理すること。
- **OOS-005 宣言されていない実装**: v0.1 は宣言された義務の裏付けのみを検証し、宣言されていない実装の存在は関知しない（R-2。README にも同宣言を一行入れる）。実装レイヤーの孤児検出・シンボル列挙の定義・上流文書の意味構造は v0.2 のスコープとする。

本システムはこれらの工程が利用する Verification Infrastructure として機能する。

## 26. 完全検証と報告

### 26.1 完全検証 OK

完全検証における OK は、宣言鎖全体に対する検査（chain_integrity / orphan_detection）と、scope に含まれる各「宣言 + コード + 証拠」の組に対する検査（target_binding / oracle_presence）がすべて `PASS` であり、テストランナーの結果を含む証拠が §6 を満たす場合に限る。一項目でも `FAIL` / `MISMATCH` / `NO_EVIDENCE` / `UNKNOWN` であれば NG。

### 26.2 簡易出力と詳細出力

利用者向けに OK / NG の簡易結果を提供する。NG の場合、どの検査が・どの状態で・どの診断ラベルとともに落ちたかを掘り下げ可能とする。

### 26.3 集約

Test 単位の結果を VO・Feature・文書単位へ集約可能とする。集約は fail-closed を基本とする。PM 等は上位単位から NG 箇所まで掘り下げられること。

### 26.4 フェーズゲートと進行条件

フェーズ・工程・ゲートごとに、進行条件として必要な検証状態（§5）と承認（§19）を定義できる。検証状態と承認は独立の軸であり（§5.5）、ゲートは両者の組合せを進行条件にできる。

例:

```text
通常開発中   : verification = PASS で進行可、approval 不要
Release gate : verification = PASS + Reviewer approval
Delivery gate: verification = PASS + Owner / PM approval
```

具体的なフェーズ名・承認ロール・必要承認数・権限 schema は下位仕様へ委譲する。
