# 層の定義と仕分け規則（2026-09-05、Owner 定義）

Owner の定義（逐語）:

> 基本仕様 = 何を実現するかを確定する
> 基本設計 = それをどんな構造で実現するかを決める
> 詳細設計 = 各部品をどう実装するかまで落とす
> 詳細設計は自然言語で記述したコードになるのは避けたい。

PM の言い換え（Owner 確認済み）: 詳細設計 = 各部品が何を持ち、何を受け取り、何を返し、どの順で確定するかを、実装が迷わない粒度まで落とす（型とデータの流れ）。

## 1. 層（6段。2026-09-05、Owner 提供の参照 `LAYERING-reference.md` を作業定義として採用）

| 層 | 配列名 | id | 答える問い |
|---|---|---|---|
| 根 | `root` | `ROOT-` | Owner の決定そのもの（Issue #11 の凍結事項 F1〜F12 と Owner 裁定。導出表「第I部（根 → 要求）」から演繹） |
| 要求 | `request` | `R-N` | なぜ必要なのか（根から `derived_from`） |
| 要件定義 | `require` | `REQ-` / `P-00N` | 何ができなければならないか |
| 基本仕様 | `spec` | `SPEC-` | 外から見てどう振る舞うか（主要な振る舞い・入出力・利用条件） |
| 詳細仕様 | `detailed_spec` | `DS-`（area `DSA-`） | 各条件で正確にどう振る舞うか（境界値・状態ごと・エラーの外部的意味・受入条件。「入力・状態・条件が決まれば結果が一意」） |
| 基本設計 | `basic_design` | `BD-`（area `BDA-`） | どのような構造で実現するか（部品・責務・境界・永続化・通信・技術選定） |
| 詳細設計 | `design` | `DES-`（area `DA-`） | 各構成要素がどの契約・制約を守って実現するか（型・状態・事前事後条件・不変条件。自然言語コードではない） |

仕様は「何を保証するか」まで。設計は「その保証をどの構造・責務で実現するか」から。辺（`derived_from`）は層をまたぐ参照だけ。6段になっても辺の種類は増えない。

### 1.1 木と辺（2026-09-05、Owner 共有の「hierarchy + trace link」モデルを採用）

- **木（hierarchy）**: 各層に「文書 > 節 > 小節 > 文」の木を持つ。見出し番号から機械的に作り、判断は要らない。木は文書構造の1本だけ（「詳細化の木」は別に持たない）。
- **辺（trace / realization）**: `derived_from` 一種のまま。文にも節にも付く。文中の引用は文の辺（5,388）、文書末尾のトレーサビリティ表（節 → 上流節、136 行）は節の辺。表を文単位に展開しない（展開すると 218,862 辺、1文あたり平均 74、最大 421 になり、文書が言っていない対応を機械が作る）。
- **辿るとき**: 文の実効的な上流 = 自分の辺 ∪ 先祖（節・文書）の辺。保存せず計算する。
- **カーディナリティ**: 縛らない。`derived_from` は並びなので N:M を表せ、1:N は観測される形。実測（2026-09-05）: 文の粒度では要求→要件・要件→基本仕様ともほぼ親1つ（例外は要件 §20 ← R-1, R-4 の 14 文）。節の粒度では N:M（基本仕様の表 45 行中 24 行が上流節2つ以上）。規範にはしない（Owner: ツールは判断しない、参照を写すだけ。「親1つ」は私が持ち込みかけた制約で、演繹上は不要）。
- **根の層（`root`、2026-09-05）**: 要件定義の導出表は「第I部（根 → 要求）」と自ら宣言し、上流欄に Issue #11 の凍結事項（F1〜F12）と Owner 裁定を書いている。したがって #11 の F 項目と裁定はノードであり、要求（R-1〜R-5）はそこから `derived_from` を持つ。要求層が根なのではなく、根は #11。これは文書からの演繹であって新しい規範ではない。
- **迷い（confidence: low）の扱い**: 参照文書の各層「定義できていれば成立」の一覧のどの項目に当たるかで決める（例: 「主要な永続化方式」は基本設計、「永続化ルール」は詳細設計。全体の構造なら基本設計、部品ごとなら詳細設計）。Owner に線引きを求めない。どの項目にも当たらない文があれば、それは所見として報告する。

## 2. 仕分けの判定（1文ずつ）

**第一の判定（2026-09-05 改訂、演繹）**: 文が `LAYERING-reference.md` の各層「定義できていれば成立」一覧の**どの項目に当たるか**を決め、その項目の層に置く。項目名を理由として記録する。例: 「〜に束縛される」「〜しない」型の不変条件は「詳細仕様: 仕様上の不変条件」、レコードの field 構成は「詳細設計: 入出力データの構造」、ID や値の形式は「詳細仕様: 入力値の範囲・形式・制約」、コマンドが何をするかは「基本仕様: 提供する機能」。どの項目にも当たらない文（文書自身についてのメタ言明、fixture の中身）は現在の層に置いたまま所見として一覧に出す。以下の手順は、項目が2つの層に似た名前で存在するときの決め手（全体か部品か、主要か条件ごとか）としてだけ使う。

抜き取りレビュー（2026-09-05、146 文）で初回の仕分けは 12.3% が一覧項目と不一致（基本仕様の層では 29%）だったため、全文を一覧項目で再判定する。

順に当てる。最初に当たった層に置く。

1. **約束か決定か。** 実装者が別の作り方を選んでも真のままなら約束（仕様）→ 1a へ。別の作り方で嘘になるなら決定（設計）→ 2 へ。
   - 1a. **主要な振る舞いか、条件ごとの正確な振る舞いか。** 「外から使うとどう振る舞うか」の粒度（提供機能、主要な入出力、正常時と異常時の外形）→ `spec`。「この入力・状態・条件ならこの結果」まで確定させる粒度（境界値、状態別、優先順位、エラーの外部的意味、不変条件、受入条件）→ `detailed_spec`。
2. **構造の決定か、部品の契約か。** システムの分け方（部品、責務、境界、adapter と core の分界、`.verify/` の構成、永続化と通信の方式、技術選定、入口の種類）→ `basic_design`。部品ごとの契約（提供・依存するインターフェース、型のフィールド、保持する状態と遷移、事前条件・事後条件・不変条件、エラーの伝播）→ `design`。
3. **コードか。** 手順の順序、ループ、分岐の実装順、言語固有の書き方を述べていて、別の書き方をした瞬間に嘘になる文 → `design` に置いたうえで `code_like: true` を付ける（削除候補。仕分けでは消さない）。

**PM の仮置き（提案。Owner の定義から私が導いたもので、Owner の裁定ではない。試験仕分けの結果と一緒に出し、違うものは止めてもらう）**:
- 「検証状態は5つのみ」→ 約束 → spec。
- 「インターフェースは CLI と MCP の2入口」→ 外から見える決定 → basic_design。
- 「`.verify/doc/<id>.yaml` に1レコード1ファイル」→ 外から見える決定（利用者が触る）→ basic_design。
- 「`SourceLocation` は `adapter, path, locator, byte_range` を持つ」→ 型 → design。
- 「`E-SCAN-016` は orphan_detection = MISMATCH を表す」→ 外から見える体系 → basic_design。
- 「`rust-cargo` adapter は第6段で Source Target を抽出する」→ 段の入出力なら design、段の中の手順なら code_like。
- 別紙C の受入条件は、約束を検証可能な形で書き直したもの → spec に置く。ただし fixture の中身の定義は basic_design。

**未解決の緊張**: 昨日の Owner 案「基本仕様＝システム概要・システム構成・機能一覧表」と、今日の判定1「別の作り方でも真なら約束 → spec」は、同じ結果にならない可能性がある。判定1のままだと状態表・Evidence 有効条件・ハッシュ束縛のような振る舞いの契約はすべて spec に残る。試験仕分けの数で確かめる。

## 3. 仕分けの出力

`docs/canonical/relayer/<fragment>.json`: `{ "<現在の id>": { "layer": "spec|basic_design|design", "reason": "<1行>", "confidence": "high|low", "code_like": false } }`。
`confidence: low` の文は Owner に一覧で出す。仕分けは文を書き換えない。

## 4. 仕分け後

`build.py relayer apply` で fragments に `layer` を書き、再ビルド。id は接頭辞が変わるので付け直し（固定は分割後）。辺は `cites`・導出表・トレーサビリティ表から再計算する。
