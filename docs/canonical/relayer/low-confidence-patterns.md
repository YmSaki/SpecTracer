## 3. クロスドキュメント一貫性チェック

5つの分類ファイル（base・det1・det2・anxA・anxC）全体（`confidence: low` に限らない）から、複数文書に共通して現れる5種の「文の種類」を選び、5つの分類器が同じ層に置いたかを確認した。根拠は各`*-report.md`の例外一覧・集計節（機械的grep、およびbase-report.md (e)節の直接記述）。

- anxA: DES-1653 → `detailed_spec`（高確信）
- anxC: DES-1707 → `detailed_spec`（高確信）
- **判定: 一致。** 5文書すべてが「条件→診断コードの精密な写像」を`detailed_spec`に置いており、文書間の不一致はない。ただし全5文書が揃って、`LAYERING.md` §2自身が挙げたPM仮置き（「`E-SCAN-016`は`orphan_detection`=`MISMATCH`を表す」→`basic_design`）とは異なる結論に達している。

### 3.2 終了コードの意味
- base: SPEC-665, SPEC-689（「終了コード体系の詳細は詳細設計へ委譲する」という一般原則・委譲）→ `spec`
- det2: §17.2セクション全体のデフォルトは`detailed_spec`（精密な条件→コード対応）だが、一般原則の再述（DES-1237, 1242）は`spec`
- anxA: DES-1264「終了コードは本冊§17.2に従う」（委譲）→ `spec`
- **判定: 一致。** 一般原則・委譲文は`spec`、条件とコードの精密な対応表は`detailed_spec`という同一の分割が3文書で独立に再現されている。

### 3.3 `.verify/` レイアウトの記述
- base: SPEC-121, SPEC-631〜637 → `basic_design`（高確信、LAYERING.md PM仮置きと一致）
- det1: §2.1「`.verify/`レイアウト」節のデフォルトは`basic_design`（18/19文）
- **判定: ほぼ一致、1件のみ内部で割れる。** det1の唯一の例外`DES-102`「基本仕様§24.1のlayoutをそのまま採用する」は、新たな構造決定を行わない追認文であるためP9（参照委任文）の理由で`spec`に低確信で分類されている。レイアウトの内容自体の分類は割れていない。

### 3.4 adapter/core境界の記述
- base: SPEC-020, SPEC-021, SPEC-076（「Rust固有処理はrust-cargo adapterが所有する」等）→ `basic_design`（高確信）
- det1: DES-401, 403, 405, 517, 518（adapter/core分界の委譲構造）→ `basic_design`（低確信だがbaseと同じ層）
- det2: DES-704, 705, 710（「coreはadapterの返却値の整合性を検証する」「core内でhashを計算する」）→ **`design`**
- **判定: 不一致。** base・det1は「どちらの部品が何を所有するか」という構造の明示を`basic_design`に置くのに対し、det2は同種の「adapter/core境界」に関わる文を、coreが満たすべき精密な事後条件契約として`design`に置いている。同じ種類の文が2つの層にまたがっている。

### 3.5 ID規則（生成・一意性・所有権）
- base §3.2「ID規則と関係リンク」: 21文中13文が節のデフォルト層（`basic_design`）と異なる。内訳は概ね、ID所有・adapter/core分界（SPEC-168, 172, 173）→`basic_design`、ID衝突・一意性の精密な扱い（SPEC-151〜158）→`detailed_spec`、ID存在・意味論の一般原則（SPEC-150, 155, 156, 159, 164）→`spec`、ULIDのpayload特性という性質記述（SPEC-163）→`spec`だが低確信で`basic_design`との境界を明記。
- det1: 生成ID書式の精密規定（DES-215, 217, 240, 626）→ `detailed_spec`
- **判定: 部分一致（精密さに応じた分割自体は一致、境界事例が残る）。** 「精密なID制約は`detailed_spec`、所有権の割当は`basic_design`」という分割はbase単独でも、base対det1でも再現されている。ただし`SPEC-163`のような「性質の記述」は`spec`と`basic_design`のどちらとも取れる境界に残っており、単一文書内でも解消されていない。

### 3.6 まとめ
5種のうち、3.1（診断コード）・3.2（終了コード）は文書間で完全に一致。3.3（`.verify/`レイアウト）・3.5（ID規則）は大枠一致だが境界事例が個別に残る。3.4（adapter/core境界）のみ、3文書にまたがる明確な不一致（`basic_design`×2 vs `design`×1）が確認された。
