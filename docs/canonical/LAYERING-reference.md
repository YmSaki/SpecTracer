# 層の定義（Owner 提供の参照文書、2026-09-05）

Owner が別の AI に整理させ、「参考になるかはわからんが」と共有したもの。逐語で保存する。作業定義として採用したのは `LAYERING.md` の側。

## 各工程が答える問い

| 工程 | 答える問い |
|---|---|
| 要求 | なぜ必要なのか |
| 要件 | 何ができなければならないか |
| 基本仕様 | 外から見てどう振る舞うか |
| 詳細仕様 | 各条件で正確にどう振る舞うか |
| 基本設計 | どのような構造で実現するか |
| 詳細設計 | 各構成要素がどの契約・制約を守って実現するか |
| 実装 | 具体的にどうコードを書くか |

```text
要求
  ↓ 「満たすには何が必要か」
要件
  ↓ 「それはどんな振る舞いか」
基本仕様
  ↓ 「曖昧さをなくすとどうなるか」
詳細仕様
  ↓ 「それをどんな構造で実現するか」
基本設計
  ↓ 「各部品が守るべき契約は何か」
詳細設計
  ↓
実装
```

**仕様は「何を保証するか」まで。設計は「その保証をどの構造・責務で実現するか」から。実装は「その設計を具体的なアルゴリズムやコードにする」段階。**

## 各層が定義できていれば成立、の一覧

- **要求**: 要求主体 / 背景・課題 / 目的 / 期待する成果 / 要求の範囲。読んで「なぜこの取り組みが必要なのか」を説明できる。
- **要件**: 必要な能力 / 対象 / 条件 / 品質要求 / 制約 / 達成判定 / 要求との対応関係。読んで「要求を満たすためには何ができなければならないか」を説明できる。機能要件と非機能要件を含む。
- **基本仕様**: 提供する機能 / 外部から与えられる入力 / 外部へ返される出力 / 主要な振る舞い / 正常時の結果 / 異常時の外部的な振る舞い / 利用条件 / 外部から観測可能な状態変化 / 機能間の主要な関係 / 仕様を満たしたか判定する条件。読んで「このシステムを外から使うとどのように振る舞うのか」を説明できる。内部構造（DB、クラス、アルゴリズム）は含まない。
- **詳細仕様**: すべての入力条件 / 入力値の範囲・形式・制約 / すべての出力結果 / 正常系・異常系・境界値・状態ごとの振る舞い / 状態遷移条件 / 例外条件 / 競合する条件の優先順位 / エラーの外部的意味 / 仕様上の不変条件 / 受入条件・検証可能な期待結果。「入力・状態・条件が決まれば、期待される結果が一意に決まる」。依然として「何をするか」の定義であり内部実装方式ではない。
- **基本設計**: システム全体の構成 / 主要コンポーネント / 各コンポーネントの責務 / コンポーネント間の境界 / 主要な依存関係 / 主要なデータの流れ / 主要な外部・内部インターフェース / データの所有主体 / 主要な永続化方式 / 主要な通信方式 / 主要な技術選定 / セキュリティ境界 / 障害境界 / 整合性境界。読んで「この仕様を、どんな部品に分け、誰に何を担当させて実現するのか」を説明できる。
- **詳細設計**: 構成要素ごとの責務 / 提供・依存するインターフェース / 入出力データの構造 / 保持する状態 / 状態遷移 / 事前条件・事後条件・不変条件 / エラーの意味と伝播方針 / データ所有権 / 永続化ルール / トランザクション境界 / 排他・並行処理上の制約 / セキュリティ上の制約 / 障害時に維持すべき条件 / 他コンポーネントとの契約 / 実装者に委ねてよい範囲。読んで「各部品が何を保証し、何を前提とし、何をしてはならないか」を説明でき、かつ「実装方法そのものは一意に固定していない」。**処理手順を自然言語で逐語的に記述するものではない**（「1. A を取得する 2. if 文で確認する…」は望ましくない）。
