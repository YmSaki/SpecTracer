# md → JSON 変換規則（移行期間）

Issue #14 の決定（JSON を正本、md は一方向エクスポート、`.verify/doc/` の文書モデルそのもの）に基づく変換の規則。
schema は `specification.schema.json`。変換は**忠実な転記**であり、内容の修正はしない。

## 1. 層と文書の対応

| 層 | 元文書 | 備考 |
|---|---|---|
| `request` | 要求・要件定義 v0.1 第I部（R-1〜R-5） | id は既存名 `R-1`〜`R-5` を残す |
| `require` | 要求・要件定義 v0.1 第II部（§1〜§28） | `P-001`〜`P-005` だけ既存名を残す。他は `REQ-NNN` |
| `spec` | 基本仕様 v0.1 | `SPEC-NNN` |
| `design` | 詳細設計 v0.1 本冊、別紙A、別紙C | area = 最上位の `##` 節（本冊 §1〜§11・§16・§17・§19、別紙A §12〜§15、別紙C §18）。area は `DA-NNN`、item は `DES-NNN`。別紙A・別紙C の区分は area の分け方で表現し、field は作らない |
| 除外 | 別紙B 実装計画、実装スケジュール、`docs/plans/` | 非規範の process 文書 |

## 2. 粒度: 1 statement = 1 つの規範文

- **規範文**とは、義務（〜しなければならない・〜とする）、禁止（〜してはならない・〜しない）、定義（〜とは〜である・〜を〜と呼ぶ）のどれか1つを述べる文。
- 1つの文に義務が2つあれば2 statement に割る。箇条書きの1項目が複数の規範を含めば割る。
- 割るときは主語を補って、それ単体で読める文にする。**語は足さない、意味は変えない。** 補うのは主語と、指示語（「これ」「同上」）の展開だけ。
- 例（基本仕様 §2.1 三層構造）: 「宣言層は…からなり Git 管理される正典である」「実装層は…」「事実層は…」の3 statement。
- `statement` は規範文そのもの。`description` は同じ箇所にある背景・理由・例・表・補足で、その statement を説明しているもの。説明でない散文は §4 の落とし先へ。

### 2.1 列挙の扱い（試験変換で出た違反の再発防止）

- **導入文 + 列挙**（「fixture は少なくとも次を表現できる。」「`target_binding` は次で定まる。」「文書鎖の各状態：…」「提供範囲外: …」）は、導入文を主語として各項目に配り、**項目ごとに完結した規範文**にする。導入文そのものは statement にしない（配った時点で吸収される）。
  - 誤: `「fixtureは少なくとも次を表現できる。」` + `「結果を検証しないTest」` + `「GUI」`
  - 正: `「fixture は、結果を検証しない Test を表現できる。」`、`「GUI は提供範囲外である。」`
- **単体で読めない statement は不可。** 名詞句だけ（「GUI」「LSP統合」）、コロン付きの断片（「文書鎖の各状態：根 document」）、指示語で終わる文（「次で定まる」「次のとおり」）は、どれも statement にならない。
- 列挙の各項目が既に完結した文なら、そのまま1項目 = 1 statement でよい（別紙C L173 の分割が手本）。
- 括弧内の診断コード・状態値（「（E-SCAN-016、`orphan_detection = MISMATCH`）」）は規範の一部なので statement に残す。括弧内の上流引用（「（本冊 §11.2）」「（要件定義 §5.3）」）は `cites` へ移し statement からは外す。

## 3. `derived_from` と `cites`

- `derived_from` は変換時には**常に空配列**。導出の確定は Owner の承認を経る別工程（§6）。
- 元 md にある上流引用は **`cites` に逐語で**記録する。例: `"（R-1）"`, `"基本仕様 §3.2"`, `"要件定義 L324"`, `"§5.1、§23"`。文書名が省略されている節番号引用は、その文書の慣習で補わず、書いてあるとおりに写す。

## 4. 規範でないものの落とし先

| 種類 | 扱い |
|---|---|
| 背景・理由・例・表で、ある statement を説明しているもの | その statement の `description` |
| 見出し行、空行、区切り線 | 何もしない（被覆検査で自動除外） |
| 「付記（非規範）: トレーサビリティ表」（各文書末尾） | dropped-log へ（理由: 非規範の導出記録）。**ただし要求・要件定義 L612 以降の「要求→要件 導出表」は落とさない**。§6 の入力なので dropped-log に `keep_for_derivation: true` で記録する |
| 目次、分冊構成表、文書の位置付け（§0）のうち規範を含まない部分 | dropped-log へ |
| 規範でも説明でもない散文 | dropped-log へ（理由を書く） |

dropped-log の形: `{ "doc", "lines": [s, e], "reason", "keep_for_derivation"? }`。

## 5. 被覆（何も黙って落とさない）

元 md の全行は、次のどれかに属さなければならない。

1. ある item の `source.lines` の範囲内（statement か description として写された）
2. dropped-log のどれかの範囲内
3. 見出し行・空行・`---`・コードフェンスの開閉行

これを機械検査する。1つでも外れる行があれば変換は不完全。

## 6. 導出の確定（変換後、Owner 承認）

1. `cites` の各引用を、指す先の候補 statement id の一覧に解決する（節引用は複数候補になる）。
2. 要求・要件定義 L612 以降の導出表の各行を候補にする（「書記導出」と明記された行は区別する）。
3. 候補一覧を Owner が行ごとに承認・却下し、承認分だけ `derived_from` へ入れる。

## 7. ID の付番

変換エージェントは `id` を付けない。後処理が (層, 文書, `source.lines[0]`) 順に決定的に付番する。1文書を変換し直しても他の文書の番号は変わらない。

## 8. 監査で見つかった13箇所の扱い

`reports/upstream-traceability-audit-2026-09-04.md` の指摘箇所は、変換では**そのまま写す**。直すのは変換後に、ノード単位の編集として別途行う。変換中に直すと diff が読めなくなり、「実装に合わせて仕様を改竄しない」規則を仕様側で破ることになる。
