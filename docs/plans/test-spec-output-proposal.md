# テスト仕様書の出力 — 要件追加と設計方針

状態: 要件文案は **Owner 承認済み（2026-10-26）** で、正本に反映した（REQ-339〜REQ-342、要件 §22）。下流の仕様（基本仕様、詳細設計、別紙A・C）と実装は、この PR の merge 後に始める（計画 v0.2 §0.3、P-005）。

## 1. 位置付け

このツールは、テストコードに `@` 注釈を埋め込み、Doxygen のようにテスト仕様書を出力する機能から始まった。のちに、実装ソースと上流仕様へのトレースを加えた。

正本には、後半の「トレース」を支える要件だけがあり、最初の「テスト仕様書の出力」に当たる要件はなかった。最も近い NFR-008（人間が VO・Test の不足、不一致、NG 理由を一覧で理解可能であること）は、検証結果の出力であり、仕様書の出力ではない。

CLI も同じ状態になっている。`main`（v0.1.0-alpha.1）にあった `test list/show` と `report` は、`develop` の CLI にない。ただし別紙A §12.2 には `vtest test show/list/query` が残っている。仕様と実装が食い違っている。

## 2. 出力するもの

1 つの Test を 1 つの項目にして、次を出す。値はすべて `scan` が adapter から受け取る `TestEntity` から取る。新しい入力は増やさない。

| 項目 | 取得元 |
|---|---|
| Test ID | `id` |
| 目的 | `intent` |
| 検証する VO とその主張 | `covers` → VO の `claim` |
| 対象（Source Target） | `targets` |
| 入力・期待・種別・ケース・関連 Test | `input` / `expect` / `kind` / `cases` / `related` |
| 所在 | `location`（adapter・path・locator） |

次の整理もつける。

- VO ごと、path ごとの目次
- 注釈がなく、管理されていない Test の一覧（`ManagedTestLink::Missing`）
- 解決できなかった `covers` / `target` の一覧

## 3. 守る性質

1. **言語に依存しない。** `TestEntity` は adapter が返す共通の形なので、Rust と synthetic adapter の Test は同じ形式で出る。（REQ-341）
2. **欠落を黙って落とさない。** 注釈のない Test、不完全な Test、解決できない参照は、一覧に必ず出す。（REQ-340）
3. **仕様書は検証結果ではない。** 仕様書に `PASS` を書かない。検証状態を併記する場合は、`verify` の値をそのまま写し、状態を新しく作らない。（REQ-342）
4. **決定論的に出す。** 同じ入力なら同じ出力になる。順序は adapter ID・path・Test ID で決める。（REQ-341）
5. **CLI と MCP は同じ JSON の形を返す。** Markdown は JSON から作る派生物であり、正本ではない。

## 5. 受入条件の案

- Rust と synthetic の混在プロジェクトで、両方の Test が同じ形式で出る（既存の混在 fixture を再利用できる）。
- 注釈のない `#[test]` が、「未管理」として出る。
- 解決できない `covers` が、省略されずに出る。
- 並べ替えた入力でも同一の出力になる。
- CLI と MCP が同じ JSON を返す。

## 7. プロの利用観点と、そこから導く設計判断

プロの開発者がこのツールを使うとき、得られる価値は次のとおり。

| 価値 | 使う場面 |
|---|---|
| コードを読まずに、各テストが何を保証するかを確認できる | レビュー、引き継ぎ、監査。注釈はテストと同じファイルにあるため、仕様書だけが古くなりにくい（Doxygen と同じ利点） |
| テスト資産の棚卸しができる | 未管理のテスト、VO に結び付かないテスト、解決できない参照が一覧で見える |
| AI が生成したテストを短時間で検収できる | 緑のテストでも、`intent` と `expect` を読めば、何を確かめているかが分かる。実装を読まなくてよい |
| 上流の文書がなくても使える | 既存プロジェクトへの途中導入（R-5）。注釈だけで始め、上流は後から足す |
| 仕様書の差分がレビューできる | 出力が決定論的なので、PR で「仕様書がどう変わったか」が差分として読める |
| 言語ごとに別のツールを使わなくてよい | Rust と他の言語が混在するリポジトリでも、同じ形式で出る |

この観点から、次の設計判断をする。いずれも下流の仕様に反映する候補であり、REQ-339〜342 の文言は変えない。

1. **上流の文書がなくても出力できる。** 上流トレースは付加情報とし、無くても欠落扱いにしない。途中導入の最初の一歩が、仕様書の出力になる。
2. **既定では検証状態を載せない。** 仕様書と検証結果は別のものとして扱う（REQ-342）。併記する場合は、明示的な指定を要する。
3. **行番号を出さない。** 所在は path と locator で示す。行番号は 1 行足しただけで全項目が変わり、差分がノイズだらけになる。
4. **未管理・解決不能の一覧は、目次の近くに置く。** 抜けを見つけることがプロの主な用途なので、末尾に埋もれさせない。
5. **ID を見出しの anchor にする。** Test ID と VO ID を anchor にすれば、レビューのコメントや他の文書から安定してリンクできる。
6. **出力は正本ではない。** 派生物であり、コミットするかどうかは利用者が決める。`.verify/cache/` を正典として手で編集しない原則は変えない。

今回は範囲に入れないが、プロにとって価値が大きい後続の候補を挙げておく。

- ソースから、それを検証する Test を逆引きする（変更影響の確認）。
- 2 つの revision の仕様書を比べて、増減だけを出す。
