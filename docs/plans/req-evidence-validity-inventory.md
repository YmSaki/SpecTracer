# 要件定義 棚卸し: 「Test が検証証拠として成立する条件」はどこまで書かれているか

2026-08-17。DA-006 の4輪の揺れ（helper 追跡 → 可視性 → 宣言 → 検証コンポーネント）の根因調査。結論: **成立条件の正の定義が要件定義に存在しない**。最初に無効化された上流成果物は DA-006 ではなく要件定義のこの欠落。

## 中核的発見

§11 の包括句「検証結果が対象実装の正しさに依存しない構造（はNG）」は、求めている正の要求 —「**検証対象の振る舞いが Test の判定結果に因果的に反映されなければならない**」— を違反類型の側から言い当てている。改訂は新概念の発明ではなく、**この句を正の成立条件へ一般化する**作業になる。

## 作業草案（Codex 整理・Owner relay 2026-08-17。文言は Owner レビュー待ち）

1. **検証証拠の成立条件（算入条件）**: Test を仕様適合性の証拠として算入するには、検証対象の振る舞いを反映する観測が存在し、その観測に基づいて期待条件への適合・不適合を識別でき、不適合が Test の非成功として反映されなければならない。
2. **依存する判定能力の信頼性**: Test が適合性判定の全部または一部を他の構成要素へ委ねる場合、その構成要素の正当性が確認されていなければ、その Test を有効な仕様適合証拠として扱ってはならない。委譲先の内部実装方式を Test 自身の成立条件とはしない。
3. **証明方式への非依存**: 成立条件を確認する方法は、検証対象や実行形態に応じて異なってよい。特定の実行形態に固有の証明方法を他の形態へ要求しない。確認不能と要求違反を区別し、確認できない事実から違反を推定しない。
4. **既存 §11 の位置付け変更**: 定数assert・対象未実行・結果未検証・自己比較等は、上記成立条件を満たさないことを決定論的に検出できる具体例として位置付ける。

設計語彙（oracle / helper / call graph / Source Target / Contract Target / assert / 到達）は要件定義に持ち込まない。「Test 一般」ではなく「**算入**」で書く（role 仕様の supporting = 管理するが算入しない、と整合）。
