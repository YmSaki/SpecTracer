## Owner 判断 3点（WHAT 層の決定。HOW は詳細設計へ委譲）

### A. 「明示的に信頼する基盤」の具体範囲
要件 §11.1 条項2 は verified / explicitly trusted の二分と終端を要求。基本仕様で信頼基盤を何と定めるか。
- **推奨**: 標準 assert 構文・test framework の failure semantics（`#[should_panic]`・Result 等）・**config の `assertion_macros` に列挙されたマクロ**を明示的信頼基盤とする。→ 既存 config が「信頼の宣言面」としてそのまま意味付けされ、新機構ゼロ。ユーザーが独自 assert マクロを信頼させたければ config に書く（宣言 = 正典の原則とも一致）。

### B. user 定義の判定委譲先の「正当性確認」として何を認めるか
- 選択肢: (i) 静的確認（委譲先の内部に信頼基盤構文が解析視界内で確認できる）(ii) supporting テストによる cover（role 仕様の B 群の本来目的）(iii) その両方を許可集合とする
- **推奨: (iii)**。確認方法の許可集合だけを WHAT で定め、解析視界の定義・探索規則は詳細設計（DA-006 再導出）へ。→ 旧「helper 1段」論争は「(i) の解析視界をどう採るか」という HOW に正しく降格される。確認できない委譲は §11.2 条項4 により UNKNOWN → 意味監査。

### C. 「成否判定を持たない」クラスを基本仕様の最小検出集合へ追加するか
現在 §7.2 の最小リスト（定数 assert / target 未呼出 / 結果未検証 / 自己比較 / 空テスト）に oracle 不在クラスが無い（DA-006 は詳細設計のみの存在 — STATAUDIT-01 の遠因）。
- **推奨: 追加する**。要件 §11.1 の直系違反クラスであり、これが入ると DA-006 の再導出が「基本仕様の最小集合の実装」という正しい位置になる。
